## Этап 1. Схема

### S1.1 Правила привилегий ✅

- Таблицы `perk_rules` (код, название, происхождение `SHIPPED`/`OWN`, константы,
  `is_active`) и `perk_rule_versions` (текст скрипта, хеш, кто и когда).
- `shop_products`: `perk_rule`, `perk_config` вместо `perk_kind`, `perk_value`.
- `user_perks`: `rule_version_id`, `config` вместо `kind`, `value`.
- Перенос данных: три вида → три поставляемых правила, значение → `{"VALUE": …}`.
- CHECK на `perk_kind`/`perk_value` снимаются вместе с колонками.

**Готово:** миграция на копии данных с купленными привилегиями всех трёх видов
переносит их без потерь; повторный прогон не падает.

Сделано миграцией `062_perk_rules.sql` поверх 059/061, а не правкой 059 —
см. §1.8 плана. Хеш версии не уникален: возврат к прошлому тексту — новая
версия.

### S1.2 Паспорт, «проверенный», согласие ✅

- `users.is_checked`, `checked_at`, `checked_by`; `users.pd_consent_at`,
  `pd_consent_version`.
- `user_passports`, `passport_access_log` — схема из §3.1 плана.
- Настройка `pd_consent_version = 1`.
- Права: разделы `checks` (view, edit), `passports` (view, edit), `perk_rules`
  (view, create, edit) в каталоге `service/permission.go`; по умолчанию
  `checks` и `passports.view` у `MODERATOR`.

**Готово:** миграция применяется; новые разделы видны в матрице ролей.

### S1.3 Доставка

- `orders.dropoff_address`, `dropoff_lat`, `dropoff_lon`, `dropoff_fias_id`,
  `orders.funded_by` (`CUSTOMER` по умолчанию, `SHOP`).
- `shop_orders.delivery_order_id`.
- Типы `SHOP_DELIVERY_HOLD`, `SHOP_DELIVERY_REFUND` (миграция без транзакции,
  как 058).
- `shop_products.dispatch_address`, `dispatch_lat`, `dispatch_lon`,
  `dispatch_fias_id`; `shop_pickup_points.is_default` с уникальным частичным
  индексом (пункт по умолчанию один).
- Узел каталога «Доставка» с поведением `delivery` — выключенным.

**Готово:** миграция применяется; существующие заказы получают `funded_by = CUSTOMER`.

## Этап 2. Привилегии-скрипты

### P2.1 Пакет `backend/perk` ✅

- Хук `rate(f)`: факты `base`, `level_percent`, `level`, `config`; ответ — число.
- Компиляция через общий `backend/script`, лимиты шагов и таймаут.
- Поставляемые правила `backend/perks/commission_multiplier`,
  `commission_discount_pp`, `commission_free` — те же формулы, что `ApplyPerk`.

**Готово:** тест сравнивает поставляемые правила с `ApplyPerk` на сетке
«база × уровень × значение» — ответы совпадают.

### P2.2 Проверка по сетке ✅

- При сохранении правила ядро прогоняет `rate` по сетке из §1.3 плана и
  отклоняет правило, если ответ не число, падает или выходит за `[0, base]`.
- Ответ сохранения содержит таблицу прогона — её показывает форма.

**Готово:** тесты на правило, возвращающее строку, отрицательное число, больше
базы, бесконечный цикл (лимит шагов).

### P2.3 Ставка через скрипт ✅

- `Levels.For` вызывает `rate` действующей привилегии, зажимает ответ в
  `[0, base]`.
- Отказ скрипта: ставка по уровню, инцидент `perk_script_failed`, подтверждение
  заказа проходит.
- Из нескольких действующих — дающая наименьшую ставку, как сейчас.

**Готово:** интеграционный тест подтверждения заказа с каждой из трёх
поставляемых привилегий и с падающим правилом; книги сходятся.

### P2.4 Товары и покупки на правилах ✅

- Валидатор товара проверяет, что правило существует и активно, константы
  подходят (прогон по сетке с константами товара).
- Покупка и ручная выдача пишут `rule_version_id` и снимок констант.
- `ApplyPerk`, `validatePerkValue`, константы `PerkKind*` удаляются.
- Окупаемость на карточке считается тем же `rate`.

**Готово:** правка собственного правила после покупки не меняет ставку по уже
купленной привилегии (тест).

### P2.5 Админ-API и товары T0.1 ✅

- `GET/POST/PUT /api/admin/shop/perk-rules`, библиотека поставляемых правил.
- Миграция или сид: четыре выключенных товара из §1.7 плана.
- Право — раздел `perk_rules` (view, create, edit); создание не перезаписывает
  существующее правило, правка не заводит новое.

**Готово:** тесты API; товары видны в админке выключенными.

## Этап 3. Паспорт и «проверенный»

### C3.1 Шифрование ✅

- `PASSPORT_ENC_KEY` (32 байта, base64) и `PASSPORT_KEY_VERSION` в окружении,
  `.env.deploy.example`, docker-compose; `PASSPORTS_DIR` — отдельный том.
- AES-256-GCM для JSON данных и для файла фото; `key_version` в строке.
- Нет ключа — приём паспортов отвечает `503`, сервер стартует.

**Готово:** тест: в базе и на диске нет открытого номера паспорта; расшифровка
другим ключом падает.

### C3.2 Паспорт владельца ✅

- `PUT /api/me/passport` (поля), `POST /api/me/passport/photo` (фото, тип по
  содержимому, как у изображений магазина), `GET /api/me/passport` — маска.
- Поля — серия, номер и дата выдачи, все обязательны. Без них — `400` с
  указанием поля.
- Правка запрещена «проверенному» — `409` с текстом «через поддержку».
- Паспорт без согласия на ПД — `403`.

**Готово:** тесты хендлеров и сервиса.

### C3.3 Паспорт в админке ✅

- `GET /api/admin/users/{id}/passport` и `/photo` — `passports.view`, каждый
  вызов пишет `passport_access_log` и `[AUDIT]`; фото с `Cache-Control: no-store`.
- `PUT`/`DELETE` — `passports.edit`; удаление снимает `is_checked`.

**Готово:** тест: просмотр без права — `403`; каждый просмотр — строка журнала.

### C3.4 «Проверенный» ✅

- `POST /api/admin/users/{id}/checked` `{checked, reason}` — `checks.edit`.
- Поставить без паспорта с фото — `409`.
- `is_checked` в `/auth/me` и в фактах поведения услуг.

**Готово:** тесты на все три перехода и снятие при удалении паспорта.

### C3.5 Согласие на ПД ✅

- Регистрация требует `pd_consent: true` и пишет версию.
- `POST /api/me/pd-consent` — для существующих пользователей.
- Черновик текста согласия `doc/personal_data_consent.md` и страница в
  приложении, как у оферты.

**Готово:** регистрация без согласия — `400`; тест записи версии.

### C3.6 Паспорт в верификации ✅

- `submission` верификации принимает блок паспорта; фото — отдельным запросом
  по `client_key`.
- Паспорт пишется заказчику с `source = VERIFICATION`, `entered_by`.
- Скрипт верификации не закрывает заказ, пока паспорт с фото не получен, если
  константа поведения `REQUIRE_PASSPORT = True` (по умолчанию `True`).

**Готово:** интеграционный тест верификации с паспортом; повтор отправки
идемпотентен.

### C3.7 Заявка на «проверенного» сама ✅

- Паспорт с фото, принятый на верификации, ставит `users.check_requested_at`:
  отдельного обращения в поддержку не нужно. Паспорта нет — не происходит
  ничего.
- Заявка ставится после фото: паспорт без снимка подтверждать нечем.
- Повторная отправка дату не сдвигает — в очереди модерации порядок задаёт
  первая просьба. Решение модератора (отметка или отказ) заявку снимает.
- Человеку уходит письмо во внутренний ящик; сбой письма заявку не отменяет.

**Готово:** интеграционный тест: заявка появилась, повтор её не сдвинул,
отметка «проверенный» её сняла.

### C3.8 Живое фото и его проверка ✅

- Ключ подписи снимка: `GET /api/me/passport/photo/key` и
  `GET /api/executor/orders/{id}/passport/photo/key`. Выводится из
  `PASSPORT_ENC_KEY` по области (`user:<id>`, `order:<id>`) — таблицы ключей
  нет.
- Загрузка фото принимает `taken_at`; подпись и метку считает
  `backend/photoproof`, вердикт пишется в `user_passports`
  (`photo_seal`, `photo_mark`, `photo_taken_at`), миграция `065`.
- Проверка скрытая: загрузку не отклоняет и человеку не показывается. Снимок
  без подписи — запись `[AUDIT]` и пометка модератору в карточке.
- Фото из админки подписи не имеет: администратор прикладывает файл.

**Готово:** интеграционный тест: неподписанный снимок — `MISSING`, подписанный
— `VALID` с временем съёмки, подпись чужой области — `INVALID`.

## Этап 4. Услуга «Доставка»

### D4.1 Точка Б

- Создание заказа принимает точку Б, если поведение требует
  (`requires_dropoff`); иначе игнорирует.
- Исполнитель видит оба адреса; подбор и радиус — от точки А.

**Готово:** тесты создания заказа с точкой Б и без неё.

### D4.2 Поведение `delivery`

- `backend/behaviors/delivery`: `visible`/`can_order` — `is_verified && is_checked`.
- Узел каталога заводит миграция S1.3 выключенным.

**Готово:** тесты допуска: не верифицирован, не проверен, оба.

### D4.3 Заказ, оплаченный из `SHOP`

- `Ledger.FundFromShop` (`SHOP → ESCROW`, `SHOP_DELIVERY_HOLD`).
- Отмена заказа с `funded_by = SHOP` возвращает удержание в `SHOP`
  (`SHOP_DELIVERY_REFUND`), а не покупателю.
- Подтверждение — обычное: исполнителю цена минус комиссия.

**Готово:** тесты книг: создание, отмена, подтверждение, спор «неизвестно».

### D4.4 Доставка покупки

- `Purchase` с `delivery: true` и адресом: проверка `is_verified && is_checked`,
  создание заказа доставки в той же транзакции, `delivery_order_id`. Точка А —
  адрес отправки товара.
- Валидатор товара: вещь с доставкой без адреса отправки не сохраняется.
- Админ-API пунктов выдачи: отметка «по умолчанию» (одна; новая снимает
  прежнюю в той же транзакции); `GET /api/admin/shop/pickup-points/default`
  отдаёт адрес для подстановки в форму товара.
- События заказа доставки двигают статус покупки (§5.3 плана); подтверждение
  гасит купон.
- Отмена покупки отменяет заказ доставки, пока вещь не забрана; после — `409`
  с подсказкой «через спор».
- Трек-номер и ручной `SHIPPED` для доставки убираются.

**Готово:** сквозной тест: покупка с доставкой → исполнитель берёт → подтверждение
→ покупка `COMPLETED`, книги сходятся.

## Этап 5. Фронтенд

### F5.1 Регистрация ✅

- Галочка согласия (обязательная) со ссылкой на текст; необязательный блок
  «Паспорт» с фото.

**Готово:** без галочки кнопка регистрации неактивна.

### F5.2 Профиль ✅

- Блок «Паспорт» (маска после сохранения), кнопка «Стать проверенным» → чат
  поддержки с подставленным текстом; бейдж «Проверен».
- Окно согласия на ПД для пользователей без него.

**Готово:** проверено в вебе.

### F5.3 Верификация у модератора ✅

- В форме верификации блок паспорта и съёмка документа; офлайн — через очередь
  фото-подтверждения, локально зашифровано, удаляется после отправки.
- Статус «Ожидает отправки», пока паспорт не на сервере.

**Готово:** сценарий без сети: данные уходят после появления сети, заказ
закрывается один раз.

### F5.3a Подсказка о статусе и ожидание ✅

- В блоке паспорта — подсказка по кнопке: что даёт «проверенный» и что заявка
  уйдёт сама. Модератор объясняет заказчику, зачем отдавать документ.
- В профиле вместо кнопки «Стать проверенным» — «Заявка отправлена», если она
  уже есть.
- В карточке пользователя в админке — бейдж «Ждёт подтверждения».

### F5.3b Съёмка паспорта и правка ✅

- Фото паспорта — камерой приложения (галереи нет); в браузере остаётся
  системный выбор, и скрытая проверка это покажет.
- Профиль и форма верификации подписывают снимок перед отправкой; ключ заказа
  берётся, пока есть сеть, — офлайн-снимок уйдёт неподписанным.
- «Изменить» в профиле открывает форму с сохранёнными данными, а не пустую.
- В карточке пользователя в админке — строка о происхождении снимка.

### F5.4 Заказ доставки

- Создание: две точки с подсказками DaData.
- Исполнитель: оба адреса, маршрут на карте.

**Готово:** проверено в вебе.

### F5.5 Магазин

- Галочка «Нужна доставка» вместо выбора способа; адрес из регистрации по
  умолчанию, можно ввести другой; для непроверенных — подсказка и «Стать
  проверенным».
- В карточке покупки — ссылка на заказ доставки и его статус.

**Готово:** проверено в вебе.

### F5.5a Админка: адрес отправки

- Форма вещи: поле «Откуда забирать» с подсказками DaData; у нового товара
  заполнено адресом пункта выдачи по умолчанию, его можно поменять.
- Справочник пунктов выдачи: отметка «по умолчанию».

**Готово:** новый товар получает адрес пункта по умолчанию; без пункта по
умолчанию поле пустое и обязательно для вещи с доставкой.

### F5.6 Правила привилегий ✅

- «Магазин → Правила привилегий»: список, редактор, шаблоны из библиотеки,
  таблица прогона по сетке.
- Форма товара `PERK`: выбор правила и константы вместо вида и значения.

**Готово:** собственное правило создаётся, проверяется сеткой и продаётся.

### F5.7 Карточка пользователя ✅

- Паспорт (по кнопке «Показать», с предупреждением о журнале), фото, «Отметить
  проверенным» / «Снять отметку» с причиной.

**Готово:** права скрывают кнопки у ролей без `passports.view` и `checks.edit`.
