## 1. Спор

Заказчик оспаривает заказ, который исполнитель отметил выполненным:
`POST /api/customer/orders/{id}/dispute` с претензией. Заказ переходит в
`DISPUTED`, спор (`order_disputes`) сразу попадает в очередь арбитража.

- Оспорить можно только свой заказ в `EXECUTED` и только обычной услуги:
  скриптовые (верификация) закрываются сами, без подтверждения заказчика.
- Открытый спор на заказ — один (частичный уникальный индекс).
- Исполнитель узнаёт о споре письмом во внутреннюю почту и на подтверждённый
  e-mail; в его списке заказ выделен цветом и бейджем «Спор».

### Кто и как закрывает спор

Первое из событий ниже; строка заказа блокируется, опоздавшее получает отказ.

| Закрытие | Эндпоинт | Деньги | Заказ | Балл |
| :--- | :--- | :--- | :--- | :--- |
| Заказчик подтвердил выполнение | `POST /api/customer/orders/{id}/confirm` | оплата исполнителю | `COMPLETED` | — |
| Исполнитель признал, что не выполнил | `POST /api/executor/orders/{id}/dispute/concede` | возврат заказчику | `CANCELED` | — (ачивка «Первое покаяние») |
| Арбитр: прав исполнитель | `POST /api/admin/disputes/{id}/resolve` `executor` | оплата исполнителю | `COMPLETED` | заказчику |
| Арбитр: прав заказчик | `… resolve` `customer` | возврат заказчику | `CANCELED` | исполнителю |
| Арбитр: неизвестно | `… resolve` `unknown` | заказчику возврат, исполнителю оплата со счёта `DISPUTES` за вычетом комиссии | `COMPLETED` | обоим |

- Деньги, закрытие спора и баллы — одна транзакция.
- `confirmTx` и `cancelTx` отказывают заказу с открытым спором: закрыть заказ
  можно только вместе со спором. Скрипты и воркеры, которые про спор не знают,
  обойти его не могут.
- Об открытии пишется исполнителю, о закрытии — обеим сторонам, в чат заказа —
  системное сообщение. Уведомления отправляются после коммита.
- Проводки решения «неизвестно» — в
  [`financial_system.md`](./financial_system.md#4d-споры-с-неизвестным-исходом-счёт-disputes).

Код: `service/dispute.go`, `service/dispute_notify.go`, `repository/dispute.go`,
`handler/dispute.go`.

## 2. Штрафные баллы

Журнал `penalty_points` — источник правды: балл остаётся строкой навсегда,
отмена (`revoked_at`) и сгорание (`expired_at`) — отметки. Баллы ведутся
отдельно по ролям `EXECUTOR` и `CUSTOMER`.

`user_penalty_status` — журнал, свёрнутый в то, что читается на каждом запросе
(активные баллы, период фото, тихая блокировка). Пересчёт идёт в той же
транзакции, что меняет журнал, под блокировкой строки состояния; несколько
наград в одной транзакции берут блокировки в постоянном порядке.

`user_penalty_flags` — факты уровня пользователя: была ли тихая блокировка и
данные мягкого бана.

### Правила (N — `penalty_points_threshold`, по умолчанию 2)

| Событие | Что происходит |
| :--- | :--- |
| Баллов роли ≥ N после начисления | период фото-подтверждения до «сейчас + `photo_requirement_months`»; новый балл продлевает от себя |
| Баллов роли ≥ 2×N после начисления | тихая блокировка на `silent_block_months` от включения; новые баллы её не продлевают |
| Нет нового балла `penalty_points_ttl_months` | баллы роли сгорают, период фото снимается; тихая блокировка — нет |
| Срок тихой блокировки вышел | баллы роли сгорают, ставится флаг «была тихая блокировка» |
| Любой балл при флаге «была тихая блокировка» | рецидив: аккаунт → `SOFT_BANNED` (причина — система) |
| Администратор отменил балл | пересчёт сразу: ниже 2×N снимается блокировка, ниже N — период |

Сроки наступают сами: воркер обслуживания (`worker/penalty_worker.go`, раз в
час) сжигает баллы и снимает истёкшие блокировки. Начисление делает то же для
своей роли до записи балла, поэтому балл после срока блокировки — уже рецидив.

### Тихая блокировка

Ничего не объявляет. Проверка встроена в предикаты допуска
(`service/eligibility.go`), через которые проходят все пути:

- исполнитель не видит заказов (рядом, карта, аукцион), не попадает в
  автоподбор, не может взять заказ или сделать ставку — отказ тот же, что у
  недоступного заказа;
- заказчик видит пустой каталог и не может создать заказ;
- заказы в работе доводятся до конца.

`GET /api/me/penalty-status` о тихой блокировке молчит.

### Мягкий бан

`SOFT_BANNED` — статус учётной записи: вход разрешён, работа закрыта, клиент
показывает экран блокировки с кнопкой «Написать в поддержку». Правила доступа —
в [`auth_service.md`](./auth_service.md#статусы-учётной-записи-и-мягкий-бан).
Ставится системой при рецидиве или администратором вручную (с причиной);
снимается переводом в `ACTIVE`.

Код: `service/penalty.go`, `service/penalty_settings.go`,
`repository/penalty.go`, `handler/penalty.go`.

## 3. Эндпоинты

| Метод | Путь | Кто / право |
| :--- | :--- | :--- |
| `POST` | `/api/customer/orders/{id}/dispute` | заказчик |
| `POST` | `/api/customer/orders/{id}/confirm` | заказчик; закрывает открытый спор |
| `POST` | `/api/executor/orders/{id}/dispute/concede` | исполнитель |
| `GET` | `/api/me/penalty-status` | любой: период фото по ролям, мягкий бан |
| `GET` | `/api/admin/disputes?status=OPEN\|CLOSED` | `disputes.view` |
| `GET` | `/api/admin/disputes/{id}/evidence` | `disputes.view`; см. [`photo_proof.md`](./photo_proof.md#5-сверка-в-арбитраже) |
| `POST` | `/api/admin/disputes/{id}/resolve` | `disputes.edit` |
| `GET` | `/api/admin/users/{id}/penalties` | `users.view` |
| `POST` | `/api/admin/users/{id}/penalties/{point_id}/revoke` | `penalties.edit` |
| `POST` | `/api/admin/users/{id}/penalties/reset-silent-flag` | `penalties.edit` |
| `POST` | `/api/admin/users/{id}/status` | `users.edit`; `ACTIVE` / `SOFT_BANNED` + `reason` / `BANNED` |

## 4. Настройки

| Ключ | По умолчанию |
| :--- | :--- |
| `penalty_points_threshold` | `2` |
| `photo_requirement_months` | `3` |
| `penalty_points_ttl_months` | `3` |
| `silent_block_months` | `6` |

Все целые, проверяются при сохранении в границах (`service/penalty_settings.go`),
редактируются в «Системных настройках», карточка «Споры, штрафные баллы и
фото-подтверждение».

## 5. Экраны

- Исполнитель: раздел «Споры по заказам» с кнопкой «Признать», баннер периода
  доп. задания.

- Общий экран мягкого бана `components/SoftBanScreen.vue`.
