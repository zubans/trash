## Этап 0. Решения

### T0.1 Ответы на открытые вопросы

Владелец продукта отвечает на §9 плана: какие привилегии выходят в первой
версии и почём — множитель, вычитание пунктов, беспроцентный день и неделя;
сроки товаров; цена беспроцентного периода (считается от средней дневной
комиссии, §9.1a); доставка; остатки по размерам.

Уже решено: «Комиссия вдвое меньше» — 30 дней за 1000 ₽; возврат привилегии —
пропорционально неиспользованным дням; возврат любой покупки — только через
чат поддержки.

**Готово:** ответы вписаны в план, раздел §9 закрыт или сужен до того, что
откладывается осознанно.

### T0.3 Проверка оферты

Черновик — [`shop_offer.md`](./shop_offer.md). Юрист проверяет формулировки
об ответственности за выбор и о порядке возврата только через чат
поддержки, заполняются реквизиты, решается вопрос с фискальными чеками.

**Готово:** служебная часть убрана из текста, редакция № 1 согласована; без
этого магазин не включается (`shop_enabled = 0`).

## Этап 1. Схема

### B1.1 Миграция `058_shop_money.sql`

- `-- +migrate no-transaction`: `ALTER TYPE ... ADD VALUE` внутри транзакции не
  работает (см. `038_order_commission.sql`).
- Типы `SHOP_PURCHASE`, `SHOP_REFUND`, `SHOP_PAYOUT`; счёт `SHOP`.
- Константы `TransactionTypeShop*` в `repository/transaction.go`,
  `AccountShop` в `repository/system_account.go`, знаки в соглашении сверки.

**Готово:** миграция применяется на чистой базе и на копии рабочей; повторный
прогон не падает; `doc/migration.md` дополнен.

### B1.2 Миграция `059_shop.sql`

- Таблицы `shop_products`, `shop_orders`, `user_perks`, `shop_pickup_points` —
  схема из §6 плана, с `CHECK` на согласованность полей рода.
- Три вида привилегии в `CHECK` на `perk_kind`; `perk_value` — `NUMERIC(6,4)`
  с проверкой по виду (множитель `(0, 1]`, пункты `> 0`, у `COMMISSION_FREE`
  значения нет); `user_perks.value` допускает `NULL`.
- `user_gifts.shop_order_id`, `orders.commission_perk_id`.
- Настройка `shop_enabled = 0`.

**Готово:** миграция применяется; `CHECK` не пускают `PERK` без срока,
`PHYSICAL` без подарка, множитель `1.5`, пункты `-1` и `COMMISSION_FREE` со
значением — проверено вставкой.

## Этап 2. Деньги

### B2.1 `Ledger`: магазин

- `Ledger.ShopCharge` — `Reserve(user → SHOP, SHOP_PURCHASE)`, ошибка
  `ErrInsufficientFunds` при нехватке.
- `Ledger.ShopRefund` — `Release(SHOP → user, SHOP_REFUND)`, счёт может уйти в
  минус (обоснование в §4.1 плана).
- `Ledger.ShopPayout` — `Payout(SHOP → DEPOSITS, SHOP_PAYOUT)` с
  `DebitAvailable` и `admin_id`.
- `SHOP` в разбивке сверки (`repository/reconcile.go`) и на экране сверки.
- Метрики `LedgerEntry` покрывают новые типы автоматически — проверить.

**Готово:** тесты книг на каждую операцию; оплата при нехватке не меняет ни
баланс, ни счёт; два параллельных вывода не уводят `SHOP` в минус.

## Этап 3. Каталог (бэкенд)

### B3.1 Репозиторий товаров и пунктов выдачи

- `repository/shop.go`: `ListProducts(filter)`, `GetProduct`, `LockProduct(tx)`
  (`FOR UPDATE`), `UpsertProduct`, CRUD пунктов выдачи.
- Остаток для витрины: `gifts.stock` для `PHYSICAL`, `CountFreeCodes` для
  `CERTIFICATE` — одним запросом на страницу, без N+1.

**Готово:** интеграционные тесты репозитория.

### B3.2 Админ-API товаров

- `handler/shop_admin.go`, маршруты из §7 плана.
- Валидация по роду: `PERK` — через общий `ValidatePerk` (B4.0), без
  подарка и вариантов, `max_qty_per_order = 1`; `PHYSICAL` / `CERTIFICATE` —
  подарок существует и того же рода; цена > 0; роли существуют в справочнике.
- Удаления нет — только `is_active = false`.
- Смена цены пишет `[AUDIT]` со старой и новой ценой.

**Готово:** тесты хендлера на каждый отказ валидатора и на успешное
сохранение каждого рода.

### B3.3 Загрузка изображений

- `POST /api/admin/shop/images`: только изображения, лимит размера, имя файла
  генерирует сервер, сохранение в `/uploads/shop/` — тем же способом, что
  вложения чата (`handler/chat.go`).
- Отдача через существующий `/uploads/` в nginx; проверить, что путь
  `shop/` не требует правки конфигурации.

**Готово:** загрузка не-изображения отклоняется; загруженный файл открывается
в браузере и в APK (`resolveFileUrl`).

### B3.4 Права

- В `permissionCatalog` группа «Магазин»: `shop` (view/create/edit),
  `shop_orders` (view/edit), `shop_revenue` (view/edit), с подсказками.
- Маршруты админки охраняются этими правами.

**Готово:** разделы видны в матрице ролей; роль только с `shop_orders.view`
получает `403` на правку товара и вывод выручки.

### B3.5 Витрина

- `GET /api/shop/products` и `/{id}`: только `is_active`, только товары,
  чьи `roles` пересекаются с ролями пользователя (пустой набор — всем).
  Товар чужой роли — `404`, а не `403`: его существование не раскрывается.
- В ответе: остаток (`in_stock`, без точного числа), цена, варианты, способы
  получения.
- `GET /api/shop/pickup-points`.
- При `shop_enabled = 0` — пустая витрина и флаг `enabled: false`.

**Готово:** тесты на фильтр по ролям, скрытый товар и выключенный магазин.

## Этап 4. Привилегии

### B4.0 Виды привилегий и валидатор

- Константы видов: `COMMISSION_MULTIPLIER`, `COMMISSION_DISCOUNT_PP`,
  `COMMISSION_FREE` — в одном месте рядом с `Levels`, вместе с функцией
  `ApplyPerk(levelPercent, base, kind, value) percent` из §3.3 плана.
- `ValidatePerk(kind, value, days)`: множитель в `(0, 1]`, пункты `> 0`,
  у `COMMISSION_FREE` значения нет вовсе, дни `> 0`. Один валидатор на
  админ-API товара, ручную выдачу привилегии и покупку: правило, написанное
  дважды, разойдётся на третьей правке.
- Неизвестный вид — ошибка, а не «оставить ставку как есть»: товар с опечаткой
  в виде не должен молча продаваться.

**Готово:** табличный тест формулы по трём видам — с уровнем и без, при
нулевой базе, при вычитании больше ставки (результат 0, не отрицательный),
при смене базовой ставки; тест валидатора на каждое запрещённое сочетание.

### B4.1 Репозиторий `user_perks`

- `Active(q, userID)` — запрос из §6 плана по всем видам комиссии; когда строк
  несколько (ошибка админа), выбирается самая выгодная покупателю через
  `ApplyPerk`.
- `NextStart(tx, userID)` — `max(now, последний expires_at)` по **всем** видам
  комиссии, под блокировкой строк пользователя, чтобы две покупки подряд не
  начались в один момент.
- `CountFuture(tx, userID)` — длина очереди для `max_active_per_user`, тоже по
  всем видам.
- `Create`, `Revoke(id, adminID)`, `ListForUser` (активная + очередь).

**Готово:** тесты: очередь из разных видов не пересекается по времени;
беспроцентный день, купленный поверх множителя, начинается после него;
отозванная не действует и не сдвигает следующие; будущая не действует до
`starts_at`; две параллельные покупки дают непересекающиеся периоды.

### B4.2 Привилегия в ставке комиссии

- `Levels.For` читает активную привилегию и применяет `ApplyPerk` после
  уровня (§3.3 плана); `Level` получает `PerkKind`, `PerkValue`, `PerkID`.
- Значение, не подходящее виду, не применяется и пишет денежный инцидент.
- Подтверждение заказа (`order.go`) и спор «неизвестно» (`dispute.go`) пишут
  `commission_perk_id` рядом с `commission_percent`.
- `commissionOnBonus` не меняется — тест фиксирует, что привилегия на
  вознаграждения не действует, включая `COMMISSION_FREE`.
- `GET` уровня исполнителя отдаёт привилегию, очередь и итоговую ставку.

**Готово:** интеграционные тесты подтверждения заказа с активной привилегией
каждого вида — комиссия вдвое меньше / меньше на 5 пунктов / ноль, книги
сходятся, `commission_perk_id` записан. Отдельный тест: при нулевой комиссии
исполнитель получает всю сумму заказа, счёт `COMMISSION` не двигается.

### B4.3 «Сейчас / с привилегией / окупаемость»

- В карточке `PERK`: ставка покупателя по уровню, ставка с этим товаром
  (через `ApplyPerk`), комиссия, заплаченная за последние 30 дней (по
  `transactions` типа `COMMISSION` с `user_id` исполнителя), и экономия,
  которую дала бы привилегия. Для `COMMISSION_FREE` экономия за срок товара
  считается от средней дневной комиссии.
- Дата начала: `now` или конец очереди (`NextStart`).
- Флаг `useless: true`, когда ставка **по уровню** равна 0.

**Готово:** тест на исполнителя с заказами за месяц по каждому виду; тест, что
во время активного беспроцентного периода следующая покупка не помечается
`useless`; тест на нулевую ставку по уровню.

### B4.4 Напоминание об окончании

- Воркер (под `leader.go`, как остальные): раз в час находит привилегии,
  истекающие в ближайшие 3 дня и без следующей в очереди, пишет письмо во
  внутреннюю почту. Отметка «напомнили» — чтобы письмо было одно.

**Готово:** тест воркера; повторный прогон не шлёт второе письмо; привилегия,
за которой стоит следующая, письма не вызывает.

## Этап 5. Покупка

### B5.1 `ShopService.Purchase`

Транзакция из §4.2 плана:

- блокировка товара, проверки активности, роли, верификации, лимитов,
  `expected_price`, `offer_version` (не текущая — `409 offer_changed`),
  количества;
- `INSERT shop_orders` с `request_id`; при конфликте уникальности — вернуть
  существующую покупку без повторного списания;
- `Ledger.ShopCharge`;
- выдача по роду: `user_perks` / `giftRepo.Issue` на каждую единицу
  (`user_gifts.shop_order_id`, вариант и адрес в `fulfillment`);
- `ErrGiftUnavailable` → откат всего, `out_of_stock`;
- для `PERK`: ставка **по уровню** 0 → `perk_useless`; очередь длиннее
  `max_active_per_user` → `limit_reached`; `starts_at` — конец очереди по всем
  видам комиссии (§3.4 плана);
- статус: `PERK`, `CERTIFICATE` — сразу `COMPLETED`; `PHYSICAL` — `PAID`;
- `domain_events: shop.purchased`.

**Готово:** тесты на каждый отказ (деньги не списаны, склад не тронут); на
повтор с тем же `request_id` (одно списание); на последнюю единицу склада при
двух параллельных покупках (одна успешна, вторая `out_of_stock` без
списания); тест книг.

### B5.2 Эндпоинты покупателя

- `POST /api/shop/orders`, `GET /api/shop/orders`, `GET /api/shop/orders/{id}`,
  `GET /api/me/perks`.
- Коды ошибок из §7 плана; тексты — через i18n-ключи, как в остальных
  отказах.
- Эндпоинта отмены у покупателя **нет**: возврат только через чат поддержки
  (§4.4 плана).
- Rate limit на покупку (`middleware/ratelimit.go`).

**Готово:** тесты хендлеров; чужую покупку нельзя прочитать.

### B5.3 Доступ

- Маршруты магазина **не** добавляются в белый список `middleware/soft_ban.go`;
  чтение «моих покупок» и купонов — добавляется (это доступ к уже купленному).
- `shop_enabled = 0` отклоняет покупку.

**Готово:** `SOFT_BANNED` получает `403 account_soft_banned` на покупку и
видит свои покупки; тест выключенного магазина.

### B5.4 Уведомления и событие

- После коммита: письмо во внутреннюю почту покупателю («Заказ №N оплачен»,
  для `PERK` — даты действия); на каждую смену статуса и отмену — тоже.
- Счётчик `PAID` для бейджа в админке.
- `shop.purchased` в outbox — чтобы ачивки могли реагировать («первая
  покупка»), сами ачивки в задачу не входят.

**Готово:** откаченная покупка не порождает письма (тест); событие видно
диспетчеру ачивок.

## Этап 6. Обработка заказов (бэкенд)

### B6.1 Статусы и погашение

- `POST /api/admin/shop/orders/{id}/status`: только переходы из §4.3 плана,
  остальное — `409`; `SHIPPED` для доставки требует трек.
- Существующее погашение купона (`RedeemCoupon`): если у купона
  `shop_order_id` и погашены все купоны покупки — покупка `COMPLETED`.
- Список `GET /api/admin/shop/orders` с фильтрами, сортировкой, пагинацией.

**Готово:** тесты переходов; погашение последнего купона закрывает покупку,
не последнего — нет.

### B6.2 Отмена админом

Единственный путь возврата: оператор делает его по обращению в чат
поддержки. Случаи и суммы — таблица §4.3 плана.

- Причина обязательна; сервер предлагает сумму: полная — для вещи, для не
  начавшейся привилегии, для сертификата до показа кода; для идущей
  привилегии — пропорционально неиспользованным дням (оферта, п. 8.6).
  Оператор может изменить сумму, но не больше `total − refunded_amount`.
- `PHYSICAL`: купоны `CANCELED` (после получения — остаются `REDEEMED`),
  склад назад по флагу. `PERK`: `revoked_at`, будущие привилегии этой покупки
  тоже. `CERTIFICATE` до показа — код обратно в пул; после показа — только с
  отметкой «партнёр подтвердил, что код не использован».
- Переход в `CANCELED` разрешён из любого статуса, включая `COMPLETED`.
- `[AUDIT]` с id администратора.

**Готово:** тесты на каждый случай таблицы; расчёт пропорциональной суммы на
границах (первый и последний день); тест книг; повторная отмена — `409`.

### B6.5 Обращения о возврате

- В ответе чата поддержки для админки сообщения пользователя размечаются
  найденными номерами покупок («№\d+», только покупки этого пользователя) —
  фронтенд рисует их ссылками. На деньги разметка не влияет.
- В `GET /api/admin/shop/orders` — признак «есть обращение»: последнее
  сообщение пользователя с номером покупки новее последнего ответа
  поддержки; и его возраст для выделения старше 5 дней.
- В карточке покупки — id чата поддержки покупателя.

**Готово:** тесты разметки (чужой номер не размечается) и признака
обращения.

### B6.3 Ручная выдача и отзыв привилегии

- `POST /api/admin/users/{id}/perks` (вид, значение, дни, причина) — без
  денег, `shop_order_id = NULL`, параметры через `ValidatePerk`; ставится в
  общую очередь по тем же правилам.
- `DELETE /api/admin/perks/{id}` — отзыв без возврата.

**Готово:** тесты; выданная вручную привилегия встаёт в очередь за купленной,
а не складывается с ней; беспроцентный день, выданный поверх множителя, не
обнуляет его оставшиеся дни.

### B6.4 Выручка

- `GET /api/admin/finances/shop`: остаток `SHOP`, продажи и возвраты за период
  по товарам.
- `POST /api/admin/finances/shop/payout` — `Ledger.ShopPayout`.

**Готово:** тесты по образцу вывода комиссии.

## Этап 9. Завершение

### Q9.1 Сквозной сценарий на стенде

1. Админ заводит привилегию и футболку, включает магазин.
2. Исполнитель пополняет баланс, покупает «×0.5»; заказ, подтверждённый после
   покупки, закрыт по половинной ставке.
3. Покупает «день без комиссии» — он встаёт в очередь за первой привилегией,
   а не поверх неё; в день его действия заказ закрывается с нулевой комиссией,
   счёт `COMMISSION` не двигается.
4. Повторная покупка продлевает очередь, а не складывает ставки.
5. Заказчик покупает футболку с доставкой, админ проводит её до `COMPLETED`.
6. Покупатель жмёт «Оформить возврат» по второй футболке, пишет в чат
   поддержки; оператор по ссылке из сообщения открывает покупку и отменяет её
   с возвратом. Так же — отказ от идущей привилегии с пропорциональным
   возвратом.
7. Админ выводит выручку. Сверка — ноль.

**Готово:** сценарий пройден в вебе и в APK.
