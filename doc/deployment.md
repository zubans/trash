# Инфраструктура, деплой и CI/CD (Infrastructure & Deployment)

Документ описывает окружения развертывания, Docker-конфигурацию и автоматические процессы CI/CD.

---

## 1. Среды развертывания

1. **Среда развертывания**:
   - Единая конфигурация через `docker-compose.yml`.
   - PostgreSQL на порту `5432`.
   - Backend на портах `8088` (HTTPS/HTTP) и `8089` (Cleartext/Mobile HTTP).
   - Nginx Reverse Proxy на порту `8443` (HTTPS).
   - Frontend (Vite dev server) локально на порту `5173`.

---

## 2. Почтовый сервер Maddy Mail Server (`maddy.conf`)

Для автоматической отправки системных писем (верификации регистраций, смены почты и восстановления паролей) в стек добавлен контейнер **Maddy Mail Server** (`foxcpp/maddy:0.7.0`).

Maddy **не хранит почту** для `moya-usluga.ru` и не обрабатывает его как локальный домен. Вместо этого он принимает письма от backend через порт `587` и отправляет их **напрямую** на MX-серверы получателей от имени `mail.moya-usluga.ru`.

- **Хост Maddy (HELO/EHLO)**: `mail.moya-usluga.ru`
- **Внутренний домен Maddy**: `healthlogin.local` (не `moya-usluga.ru`)
- **Системный ящик отправителя**: `system@moya-usluga.ru`
- **Авторизационная БД для backend (Persistent Volume)**: `maddy_data` (сохраняется при перезапусках контейнеров).
- **Конфигурация**: [`maddy.conf`](../maddy.conf)
- **Порты**: `25` (SMTP, входящие соединения отклоняются), `587` (Submission для backend), `143` (IMAP, не используется).

### Настройка учётной записи для backend

После первого запуска (или при смене пароля) в Maddy должна существовать учётная запись, под которой backend авторизуется для отправки почты. Создать/обновить её можно командой:

```bash
docker compose exec mailserver /bin/maddy -config /data/maddy.conf creds create system@moya-usluga.ru
```

Пароль должен совпадать со значением `SMTP_PASSWORD` в `.env` (по умолчанию `systempass123` для локальной разработки; в проде обязательно задайте свой).

## 2.1. Мониторинг

Prometheus, Grafana, Alertmanager и экспортеры подключаются отдельным overlay-файлом [`docker-compose.monitoring.yml`](../docker-compose.monitoring.yml):

```bash
make monitoring-up
```

Файл отдельный сознательно: приложение должно подниматься и перезапускаться без мониторинга, а сломанная Grafana не должна мешать старту бэкенда. Все интерфейсы слушают только `127.0.0.1` и открываются через SSH-туннель. См. [`monitoring.md`](./monitoring.md).

## 4. Автоматизация CI/CD (GitHub Actions)

В репозитории настроен автоматический Workflow (`.github/workflows/deploy.yml`):

1. **Trigger**: Push в ветку `main`.
2. **`changes`**: определяет, какую половину стека затронул push (см. ниже).
3. **`test`**: сборка, `go vet`, тесты бэкенда и фронтенда. Выполняется всегда.
4. **`test-db`**: тесты на настоящем Postgres (`make test-db`, см. ниже). Выполняется всегда, **параллельно** с `test`.
5. **`build-and-push`** → **`deploy`** (приложение), после `test` и `test-db`:
   - Сборка Docker-образов бэкенда (`healthlogin-backend`) и фронтенда (`healthlogin-frontend`) и пуш в Docker Hub.
   - Подключение к серверу по SSH, `make restart`, сборка Android-релиза.
   - Автоматический запуск SQL-миграций БД при старте бэкенда.
6. **`deploy-monitoring`** (мониторинг): выполняется **параллельно** с `deploy`.

### Тесты на базе

E2E потока «заказчик — исполнитель», интеграционные тесты заказа, сверка денег, адреса и лидер воркеров работают только с настоящим Postgres. Обычный `go test ./...` без базы их **молча пропускает**, поэтому у них своя цель:

```bash
make test-db
```

Она поднимает одноразовый Postgres в отдельном контейнере (порт `55432`), применяет миграции, гоняет `go test ./...` с базой и убирает контейнер — в том числе при провале. Рабочую `healthlogin_db` цель не трогает: тесты пишут данные. Под этой целью выставлен `TEST_DB_REQUIRED=1`, и тест, которому не досталось базы, **падает**, а не пропускается — иначе недоступная база дала бы зелёный прогон, не проверивший ничего.

В CI то же самое делает job `test-db`; деплой приложения ждёт его наравне с `test`. Мониторинг его не ждёт: в образы приложения он не попадает.

### Две независимые ветки деплоя

`deploy` и `deploy-monitoring` идут параллельно и не зависят друг от друга. Правка алерта, дашборда или пробы **не пересобирает образы приложения, не перезапускает сервисы и не собирает APK**.

Решение принимает job `changes`. Правило намеренно записано как **запрещающий** список — «здесь только файлы мониторинга, значит деплой приложения пропускаем», — а не как разрешающий список путей приложения: неизвестный файл тогда деплоится как раньше, а не перестаёт деплоиться молча.

| Изменение | `deploy` | `deploy-monitoring` |
| :--- | :---: | :---: |
| `monitoring/**`, `docker-compose.monitoring.yml` | — | ✅ |
| `backend/metrics/**` | ✅ | — |
| `backend/cmd/opsbot/**` | ✅ | ✅ |
| `backend/money/**`, `backend/repository/reconcile.go` | ✅ | ✅ |
| `Makefile`, `backend/go.mod` | ✅ | ✅ |
| Всё остальное | ✅ | — |
| `workflow_dispatch`, force push | ✅ | ✅ |

`backend/metrics/` относится к приложению, а не к мониторингу: этот код **компилируется в бинарник бэкенда**, поэтому его правка требует пересборки образа.

Ops-бот, наоборот, живёт в мониторинге, хотя лежит в `backend/cmd/opsbot/`: его образ собирает `docker-compose.monitoring.yml`. Пока этого пути не было в списке, правка бота проходила тесты, деплоила приложение и оставляла на сервере старого бота — так починка ответа сверки не доехала до прода. Рядом по той же причине стоят `backend/money/` и `backend/repository/reconcile.go`: бот разбирает ответ сверки типом бэкенда, и смена формата в этих файлах требует пересобрать бота.

### Почему параллельный запуск безопасен

Оба job'а работают с одним каталогом на сервере, поэтому:

- **`git pull` под `flock`.** Два параллельных pull дерутся за `index.lock`; блокировка охватывает только pull.
- **Отдельный `.env.monitoring`.** Деплой приложения перезаписывает `.env` целиком на каждом запуске, так что дописывать туда переменные мониторинга означало бы терять их при следующей гонке. Compose получает оба файла: `--env-file .env --env-file .env.monitoring`.
- **`make monitoring-up` использует `--no-deps`.** Иначе `depends_on` подняли бы `db` и `frontend` ровно в тот момент, когда `make restart` их останавливает. Экспортеры просто ретраятся, пока цель не вернётся, — это и есть правильное поведение.
- **Мониторинг ничего не перезапускает в приложении**, а приложение не трогает контейнеры мониторинга: `make restart` работает только с базовым compose-файлом.
- **`concurrency` на уровне workflow**: два *запуска* не идут по серверу одновременно, новый ждёт, а не отменяет предыдущий — недоделанный деплой хуже медленного.

### Правила проверяются до применения

`deploy-monitoring` вызывает `make monitoring-check` (`promtool`) **до** `make monitoring-up`. Prometheus спокойно стартует с невалидным выражением в правиле — он просто никогда его не вычислит, а это худший из возможных отказов для мониторинга.

После старта job перезапускает Alertmanager и дёргает reload Prometheus: изменение примонтированного файла само по себе не пересоздаёт контейнер, поэтому иначе правки конфигов не применились бы.

### Секреты и переменные для мониторинга

| Имя | Тип | Обязателен |
| :--- | :--- | :--- |
| `TELEGRAM_BOT_TOKEN` | secret | да |
| `TELEGRAM_CHAT_ID` | secret | да |
| `GRAFANA_ADMIN_PASSWORD` | secret | да |
| `GRAFANA_ADMIN_USER`, `GRAFANA_ROOT_URL` | variable | нет |

Пароль базы мониторинг берёт из `.env`, который пишет деплой приложения, — дублировать его во втором файле значило бы завести второе место для утечки и ротации. Поэтому **первый** деплой мониторинга требует, чтобы приложение уже разворачивалось хотя бы раз; если `.env` нет, job останавливается с внятной ошибкой.
