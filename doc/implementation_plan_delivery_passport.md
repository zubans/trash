# План: привилегии-скрипты, доставка исполнителем, паспорт и статус «проверенный»

Статус: **проект**; §1 (привилегии-скрипты) и §2–§4 (паспорт, «проверенный»,
согласие) — **реализовано**, отступления в §1.8 и §4.1. Разбивка на задачи —
[`tasks_delivery_passport.md`](./tasks_delivery_passport.md).

Документ — продолжение магазина ([`shop.md`](./shop.md)) по итогам решений T0.1
([`tasks_shop.md`](./tasks_shop.md)). Решения владельца продукта:

| Вопрос | Решение |
| :--- | :--- |
| Привилегии | Правило привилегии — **скрипт в админке**, как собственная ачивка. В Go формул нет |
| Цены | «Комиссия вдвое меньше» и «минус 5 пунктов» — 1000 ₽ на 30 дней; «день без комиссии» — 100 ₽; «неделя без комиссии» — 500 ₽ |
| Доставка мерча | Отмеченная галочка «Нужна доставка» **создаёт заказ исполнителю** на новую услугу «Доставка» — из пункта А в пункт Б. Оплата исполнителю **включена в цену товара** |
| Кто допускается к доставке | **Только заказчик** должен быть верифицирован и проверен. Исполнитель — любой, как в обычной услуге |
| Новый статус пользователя | **«Проверенный»**: в системе есть паспорт и фото паспорта. Ставит модератор руками в админке после обращения в поддержку |
| Паспорт | Своя таблица: данные и фото документа. **Шифруется**, каждый просмотр пишется в аудит. Заполняется при регистрации (необязательно) или при верификации |
| Регистрация | Обязательная галочка согласия на хранение и обработку персональных данных |
| Размеры мерча | Общий склад на товар — как сейчас |
| Оферта | Публикуется черновиком, юрист смотрит в приложении |
| Проверка в APK | После деплоя |

## 1. Привилегии как скрипты

### 1.1 Что меняется

Сейчас вид привилегии — одно из трёх значений `perk_kind`, а формула —
`switch` в `ApplyPerk` (`backend/service/perk.go`). Новое правило требует
выкатки. Теперь привилегия устроена как ачивка ([`achievements.md`](./achievements.md)):

* **правило** — скрипт на Starlark, общий рантайм `backend/script`;
* **поставляемые** правила приезжают со сборкой (`backend/perks/<код>`): это
  три нынешних вида. Их включают, выключают и настраивают константами, но не
  правят;
* **собственные** пишутся в админке («Магазин → Правила привилегий»): код,
  константы, скрипт. Скрипт компилируется до сохранения; не компилируется —
  не сохраняется;
* товар `PERK` ссылается не на `perk_kind`, а на **правило и его константы**:
  «Комиссия вдвое меньше» — правило `commission_multiplier` с `VALUE = 0.5`.

### 1.2 Контракт скрипта

```python
MANIFEST = {
    "title": "Комиссия вдвое меньше",
    "description": "Ставка комиссии умножается на VALUE",
}

VALUE = 0.5          # константа; товар может переопределить её своим ключом

def rate(f):
    # f.base          — базовая ставка платформы, %
    # f.level_percent — ставка по уровню исполнителя, %
    # f.level         — уровень исполнителя
    # f.config        — константы правила, слитые с настройками товара
    return f.level_percent * f.config["VALUE"]
```

Скрипт **только считает число**. Он не видит ни заказ, ни пользователя, кроме
уровня, не двигает деньги и не выбирает, чья привилегия действует. Всё прочее
держит ядро:

* зажим результата в `[0, base]` — как сейчас в `ApplyPerk`;
* очередь привилегий, «одна действующая в момент времени», лимит очереди;
* выбор самой выгодной покупателю, если действующих вдруг несколько;
* лимиты рантайма: шаги и таймаут, как у скриптов услуг.

### 1.3 Скрипт на пути подтверждения заказа

[`achievements.md`](./achievements.md) держит правило «Starlark на пути
подтверждения заказа не запускается никогда». Привилегия-скрипт его нарушает:
ставка по уровню известна только в момент подтверждения, поэтому `rate`
вызывается именно тогда. Это **осознанное исключение**, и вот как оно
ограничено:

* `rate` — чистая арифметика над четырьмя числами. Скрипт скомпилирован
  заранее, вызов идёт с жёстким лимитом шагов;
* при сохранении правила ядро прогоняет `rate` по сетке (базовая ставка 0, 5,
  10, 20 и уровни от 0 до максимального полезного) и отклоняет правило, если
  хоть один ответ не число или выходит за `[0, base]`;
* если `rate` всё же упал при подтверждении, заказ закрывается по ставке
  **по уровню** (без привилегии), пишется денежный инцидент `perk_script_failed`,
  а владелец привилегии попадает в список на компенсацию в админке. Подтверждение
  заказа из-за скрипта не падает никогда.

### 1.4 Версии правил

Купленная привилегия не должна менять смысл после покупки. Поэтому правка
собственного правила создаёт **новую версию**, а `user_perks` ссылается на
версию и хранит снимок констант на момент покупки. Товар всегда продаёт
текущую версию. Поставляемые правила версионируются сборкой: их текст меняет
только релиз, прошедший ревью, и строки версии у них нет.

### 1.5 Модерация

Раздел «Правила привилегий» в админке с правом `perk_rules` (view, create, edit):
редактор скрипта, библиотека поставляемых правил как шаблоны, результат
прогона по сетке из §1.3 прямо в форме — админ видит таблицу «база / уровень →
ставка» до сохранения.

### 1.6 Миграция данных

* Три нынешних вида становятся поставляемыми правилами `commission_multiplier`,
  `commission_discount_pp`, `commission_free`.
* `shop_products.perk_kind/perk_value` → `perk_rule` + `perk_config` (`{"VALUE": …}`).
* `user_perks.kind/value` → `rule_version_id` + `config`. Уже купленные
  привилегии ведут себя как раньше: поставляемые правила считают ровно то же,
  что `ApplyPerk`. Тест сравнивает старую и новую формулы на сетке.
* `ApplyPerk` и `switch` по видам удаляются.

### 1.7 Товары по решению T0.1

Миграция заводит **выключенными** четыре товара — включает их администратор:

| Товар | Правило | Константы | Срок | Цена |
| :--- | :--- | :--- | :--- | :--- |
| Комиссия вдвое меньше | `commission_multiplier` | `VALUE = 0.5` | 30 дней | 1000 ₽ |
| Комиссия минус 5 пунктов | `commission_discount_pp` | `VALUE = 5` | 30 дней | 1000 ₽ |
| День без комиссии | `commission_free` | — | 1 день | 100 ₽ |
| Неделя без комиссии | `commission_free` | — | 7 дней | 500 ₽ |

### 1.8 Как сделано и где отступили

* **Миграция `062_perk_rules.sql`, а не правка 059.** В ветке магазина поверх
  059 уже есть 061, и правка 059 в двух ветках конфликтовала бы при слиянии;
  заодно стенды, где 059 применена, переносят данные.
* **У поставляемых правил нет строк версии** (§1.4): у их привилегий
  `rule_version_id` пуст, ключ в движке — код правила.
* **Снимок констант полный** — вместе с умолчаниями правила. Иначе релиз,
  поменявший умолчание поставляемого правила, тихо изменил бы проданные
  привилегии.
* **Хеш версии не уникален.** Возврат к прошлому тексту — новая версия: иначе
  текущей осталась бы та, от которой отказались. Сохранение без правок версии
  не делает.
* **Сетку проходит не только правило, но и товар**: сохранение товара, покупка
  и ручная выдача гоняют правило с константами товара. Карточка покупателя
  считает ставку без сетки (`PerkRules.Preview`) — её смотрят часто.
* **Экономия на карточке — одна формула для любого правила**: доля снятой
  комиссии от уплаченной за 30 дней, в пересчёте на срок привилегии. Особый
  случай «беспроцентного периода» в коде исчез вместе с видами.
* **Клиент не знает ни одного правила.** Покупатель видит название товара,
  админка — название правила с подставленными константами («Комиссия
  умножается на 0.5»), формула везде одна: «7 % → 3.5 %».
* Код: `backend/perk` (движок, сетка), `backend/perks` (поставляемые),
  `service/perk_rules.go`, `handler/perk_rules.go`,
  `frontend/src/pages/admin/ShopPerkRules.vue`.

## 2. Статус «проверенный»

Отдельный флаг, не смешанный ни со статусом учётной записи
(`ACTIVE`/`SOFT_BANNED`/`BANNED`), ни с верификацией (`is_verified`):

| Флаг | Что значит | Кто ставит |
| :--- | :--- | :--- |
| `is_verified` | модератор сверил ФИО и дату рождения с документом | услуга верификации или галочка админа |
| `is_checked` | в системе есть паспорт и фото паспорта, и модератор их просмотрел | **только руками**, в админке |

* **Статусы независимы в обе стороны.** «Проверенный» не даёт верификации, и
  верификация не даёт «проверенного»: `SetChecked` трогает только
  `is_checked`/`checked_at`/`checked_by`, верификация — только `is_verified`.
  Это разные вопросы: верификация — сверили ФИО и дату рождения с документом,
  «проверенный» — документ лежит в системе и модератор его смотрел.
* Поэтому и значок свой: там, где показывается «Верифицирован» — в списке
  пользователей админки и в кабинете рядом с телефоном, — рядом появляется
  «Проверен». Внутри профиля он тоже остался, в карточке паспорта.
* Колонки `users.is_checked`, `checked_at`, `checked_by`.
* Поставить можно, **только если у пользователя есть паспорт с фото**; иначе
  `409`. Удаление паспорта снимает `is_checked` в той же транзакции.
* Право — новый раздел `checks` (view, edit). По умолчанию у `MODERATOR` и `ADMIN`.
* **Заявку никто не пишет руками.** Как только паспорт становится полным — есть
  данные и есть фото, — сервис сам ставит `users.check_requested_at` и пишет
  человеку письмо. Это одинаково для всех путей: профиль, регистрация с
  последующим фото, паспорт, внесённый модератором на верификации. Обращаться в
  поддержку не нужно, и кнопки «Стать проверенным» в профиле больше нет.
* Паспорта или фото нет — не происходит ничего: подтверждать нечем. Повторная
  отправка дату не двигает — очередь модерации идёт по первой просьбе.
* Очередь заявок — **отдельная страница админки** `/admin/check-requests`
  (право `checks.view`), а не чат поддержки: заявка появляется без обращения, и
  чата у неё нет. В строке видно, сколько человек ждёт, есть ли фото и что
  говорит о нём скрытая проверка (§3.4); «Открыть паспорт» ведёт в ту же
  карточку, где ставят отметку.
* В профиле слово-статус «Проверенный» нажимается: подсказка объясняет, что
  статус даёт и что заявка уходит сама.
* Заявку закрывает решение модератора: и отметка, и отказ снимают
  `check_requested_at`.
* В форме верификации — подсказка по кнопке: что даёт «проверенный» и что
  заявка уйдёт сама. Её читает тот, кто верифицирует, и объясняет заказчику.
* Пароль и профиль разделены: смена пароля — своя страница `/password` со
  ссылкой в меню кабинета, в профиле её нет. Дата рождения у подтверждённого
  аккаунта не правится вовсе — кнопки «Сохранить» там нет, только строка о том,
  что смена идёт через поддержку.
* В карточке пользователя в админке — бейдж «Проверен», бейдж «Ждёт
  подтверждения» по непустому `check_requested_at`, кнопка «Отметить
  проверенным» и «Снять отметку» с обязательной причиной, `[AUDIT]` на каждое
  изменение.

## 3. Паспорт

### 3.1 Данные

```sql
CREATE TABLE user_passports (
    user_id        UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    -- Всё, что идентифицирует человека, хранится шифротекстом (AES-256-GCM,
    -- ключ PASSPORT_ENC_KEY из окружения). База без ключа паспортов не раскрывает.
    data_enc       BYTEA NOT NULL,     -- JSON: серия, номер, дата выдачи — и ничего больше
    photo_path     TEXT NULL,          -- зашифрованный файл вне /uploads
    source         VARCHAR(16) NOT NULL CHECK (source IN ('REGISTRATION', 'VERIFICATION', 'ADMIN')),
    entered_by     UUID NULL REFERENCES users(id),   -- модератор при верификации
    key_version    INT NOT NULL,       -- для ротации ключа
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE passport_access_log (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL,         -- чей паспорт
    viewer_id   UUID NOT NULL REFERENCES users(id),
    action      VARCHAR(16) NOT NULL CHECK (action IN ('VIEW', 'VIEW_PHOTO', 'WRITE', 'DELETE')),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

* **Полей ровно три: серия, номер и дата выдачи.** «Кем выдан» и код
  подразделения не хранятся вовсе — чего нет, то не утечёт, а для сверки
  личности они не нужны. ФИО и дата рождения в паспорт не дублируются: они
  есть в учётной записи и сверяются при верификации.
* Фото к записи паспорта необязательно, но без него статус «проверенный» не
  ставится (§2).
* **Шифруется всё поле данных целиком**, одним JSON: искать по номеру паспорта
  не нужно. Если понадобится проверка «такой паспорт уже есть у другого
  аккаунта» — добавим отдельный `HMAC` номера, сам номер открытым не
  хранится.
* **Фото** лежит в `PASSPORTS_DIR` вне `uploads`, зашифрованным тем же ключом.
  Маршрут `/uploads/*` до него не дотягивается. Отдаётся только админским
  эндпоинтом, который расшифровывает файл на лету, с `Cache-Control: no-store`.
* **Читать** — право `passports.view`; каждый показ данных и фото пишется в
  `passport_access_log` и в `[AUDIT]`. **Писать** могут владелец (при
  регистрации и в профиле, пока он не «проверенный»), модератор при
  верификации и админ с `passports.edit`.
* Владелец видит свой паспорт маской: «45 ** ****12, выдан 2015». Полные данные
  после сохранения наружу не отдаются никому, кроме `passports.view`.
* Без ключа `PASSPORT_ENC_KEY` сервер стартует, но приём паспортов выключен и
  отвечает `503`: хранить паспорт открытым нельзя даже временно.

### 3.2 Где заполняется

1. **При регистрации** — необязательный блок «Паспорт»: поля и фото. Регистрация
   без него проходит как сейчас.
2. **В профиле** — те же поля, пока пользователь не «проверенный». После
   отметки правка идёт через поддержку: иначе проверенный паспорт можно
   подменить. Форма правки открывается **заполненной** — `GET /me/passport/data`
   отдаёт владельцу его данные целиком и пишет обращение в журнал. Маска — для
   показа сохранённого, а не для правки: перенабирать то, что уже вводил,
   человек не должен.
3. **При верификации** — модератор на месте вводит данные паспорта и фотографирует
   документ. Это часть услуги верификации: форма `submission` получает блок
   паспорта, фото уходит тем же путём, что снимки фото-подтверждения.

### 3.3 Модератор без сети

Модератор при верификации может быть офлайн. Паспорт идёт через ту же
**очередь отправки**, что фото-подтверждение (`frontend/src/modules/photo-proof`):

* данные формы и фото пишутся в локальное хранилище устройства
  **зашифрованными** ключом сессии, а не открытым текстом;
* при появлении сети очередь отправляет попытку (`submission`), затем фото;
  повтор идемпотентен по `client_key`, как у снимков;
* заказ верификации не закрывается, пока паспорт не дошёл до сервера:
  исполнитель видит «Ожидает отправки», а у сервера нет ничего, что можно
  было бы закрыть;
* после успешной отправки локальная копия удаляется сразу, а не по таймеру.

Сверка ФИО и даты рождения остаётся какой была. Данные паспорта сохраняются
заказчику (`source = VERIFICATION`, `entered_by` — модератор), но статус
«проверенный» сами по себе **не ставят**: его ставит человек в админке (§2).
Заявку на статус паспорт с фото создаёт сам (§2).

### 3.4 Живое фото и скрытая проверка

Фото документа принимается **только живой съёмкой**: в приложении открывается
камера (`CameraSource.Camera`), выбора из галереи нет. Браузеру своей камеры не
дать — там остаётся системный выбор файла, и запретить его нельзя.

Поэтому у снимка есть вторая, **скрытая** сторона. Приложение перед съёмкой
берёт ключ (`GET /me/passport/photo/key`,
`GET /executor/orders/{id}/passport/photo/key`), подписывает им снимок и
вкладывает в изображение незаметную метку. Считает это тот же код, что и для
снимков заказов (`backend/photoproof`, `frontend/src/modules/photo-proof`): вторая
реализация подписи разошлась бы с первой на первой же правке.

* Ключ **выводится** из ключа паспортов (`PASSPORT_ENC_KEY`) по области —
  `user:<id>` для своего паспорта, `order:<id>` для паспорта заказчика на
  верификации. Ни таблицы разовых ключей, ни своей переменной окружения не
  нужно, а подпись одной области в другой не годится.
* В подпись входит время съёмки по часам телефона (`taken_at`). Без него
  проверять нечего, и вердикт будет «подписи нет».
* Вердикт хранится рядом с паспортом (`photo_seal`, `photo_mark`, миграция
  `065`) и виден **модератору** в карточке пользователя: «снято в приложении»,
  «снято в приложении, файл пересохранён», «подписи приложения нет».
* Проверка **ничего не запрещает**: загрузка не отклоняется, человеку о ней не
  говорят. Это подсказка тому, кто решает про «проверенного», и запись
  `[AUDIT]`, а не отказ.
* Ключ исполнитель берёт, пока сеть есть: у двери её может не быть, а подписать
  снимок надо там же, где его делают. Офлайн с самого начала — снимок уйдёт без
  подписи, и вердикт это покажет.
* Фото, которое загружает администратор из админки, подписи не имеет по
  определению: он прикладывает файл, а не снимает. Кто внёс — видно по
  `source = ADMIN`.

### 3.5 Аудит документов

Журнал `passport_access_log` пишется с самого начала (§3.1), но читать его было
негде. Теперь у него два входа:

* **В карточке пользователя** — кнопка «Кто смотрел паспорт» на вкладке
  «Паспорт», последние 20 обращений: когда, что сделал, кто.
  `GET /api/admin/users/{id}/passport/access`, право `passports.view`.
* **Отдельная страница** `/admin/document-audit` и пункт меню «Аудит
  документов» — весь журнал с фильтрами по телефону (и субъекта, и
  смотревшего), по действию и без обращений к своему паспорту; постранично.
  `GET /api/admin/passport-access`, новое право `document_audit.view`.

Право на аудит **не открывает паспортных данных**: на странице их нет и быть не
должно — она отвечает на вопрос «кто смотрел», а не «что написано в паспорте».
Поэтому безопасник может получить аудит, не получая паспортов. По умолчанию
право есть только у ADMIN (он суперпользователь), остальным его выдают руками.

Чтение журнала в журнал не пишется: иначе каждое чтение множило бы само себя.

## 4. Согласие на обработку персональных данных

* При регистрации — обязательная галочка «Согласен на хранение и обработку
  персональных данных» со ссылкой на текст согласия. Без неё регистрация не
  проходит — и на клиенте, и на сервере.
* Хранится `users.pd_consent_at` и `users.pd_consent_version`, как редакция
  оферты у покупки.
* Текст согласия — черновик в `doc/personal_data_consent.md`, публикуется так
  же, как оферта: страницей в приложении, юрист смотрит там.
* **Уже зарегистрированные** пользователи получают окно согласия при следующем
  входе. Без согласия работает всё, что работало, кроме паспорта: заполнить его
  и стать «проверенным» без согласия нельзя.

### 4.1 Как сделано и где отступили (§2–§4)

* **Миграция `063_passports.sql`.** Флаг «проверенный» и согласие — колонки
  `users`, как в плане; паспорт и журнал доступа — свои таблицы. Модератор по
  умолчанию получает `checks.view`, `checks.edit` и `passports.view`; правка
  паспорта (`passports.edit`) — только администратору.
* **Источник паспорта `OWNER`, а не `REGISTRATION`:** владелец заполняет его и
  при регистрации, и в профиле, и различать эти случаи незачем.
* **Фото при регистрации не принимается.** Регистрация идёт без входа, а фото —
  отдельной загрузкой; оно прикладывается в профиле сразу после входа. Поля
  паспорта при регистрации проверяются до создания учётной записи.
* **Паспорт в верификации держит ядро, а не скрипт.** Поведение объявляет
  `require_passport` (у верификации — константа `REQUIRE_PASSPORT = True`), и
  сверку данных ядро не принимает, пока паспорт заказчика с фото не на сервере
  (`409 passport_required`). Скрипту не нужно помнить, пришёл ли паспорт, и
  заказ не повисает без документа. Паспорт модератор вносит своим эндпоинтом
  `PUT /api/executor/orders/{id}/passport` и `/passport/photo` — только по
  своему заказу услуги с `require_passport`.
* **Без сети** паспорт встаёт в очередь фото-подтверждения действием
  `passport`. Данные и фото шифруются на устройстве ключом AES-GCM, созданным
  неизвлекаемым и хранящимся в IndexedDB (`modules/photo-proof/sealer.ts`);
  после отправки удаляются сразу. Где шифра нет, паспорт без сети не
  принимается. Сверка по-прежнему требует сети: сервер отвечает сразу.
* **Статус без данных.** `GET /api/admin/users/{id}/passport/status` — есть ли
  паспорт и фото, стоит ли отметка, дано ли согласие — право `checks.view`, в
  журнал не пишется: иначе каждое открытие вкладки было бы «просмотром
  паспорта».
* **Согласие при регистрации** проверяет обработчик, а отметку ставит
  `AuthService` (`WithConsent`) при создании учётной записи. Окно согласия для
  остальных — с кнопкой «Позже»: без согласия работает всё, кроме паспорта.
* **Ключ** `PASSPORT_ENC_KEY` добавлен в секреты деплоя (`deploy.yml` пишет его
  в `.env`) и в `docker-compose`; фото — отдельный том `passports_data`. Без
  ключа сервер стартует, а приём паспортов отвечает `503`.
* По пути исправлено: поле выбора файла в чате поддержки было видно — класс
  `d-none` нигде не определён.

## 5. Услуга «Доставка»

### 5.1 Что это

Новый узел каталога «Доставка»: исполнитель забирает вещь в пункте А и отвозит
в пункт Б. Устроена как особая услуга со скриптом поведения, как верификация
([`service_behaviors.md`](./service_behaviors.md)):

* поставляемое поведение `delivery` (`backend/behaviors/delivery`);
* `visible` / `can_order`: заказчик **верифицирован и проверен**
  (`is_verified && is_checked`). Факт `is_checked` добавляется в факты
  пользователя;
* исполнитель — любой на смене, по обычным правилам подбора: радиус считается
  от точки А;
* цена — из варианта каталога, как у остальных услуг (фиксированная).

### 5.2 Два адреса у заказа

Сейчас у заказа один адрес — туда исполнитель едет за мусором. У доставки их
два. Точка А остаётся в нынешних полях адреса заказа: подбор исполнителей,
радиус, карта и геозоны работают без изменений. Точка Б добавляется рядом:

```sql
ALTER TABLE orders
    ADD COLUMN dropoff_address TEXT NULL,
    ADD COLUMN dropoff_lat DOUBLE PRECISION NULL,
    ADD COLUMN dropoff_lon DOUBLE PRECISION NULL,
    ADD COLUMN dropoff_fias_id TEXT NULL;
```

Поведение объявляет в манифесте `requires_dropoff: True`. Ядро тогда требует
точку Б при создании заказа, а исполнитель видит оба адреса и маршрут на карте.

### 5.3 Доставка покупки из магазина

Способ получения `DELIVERY` у вещи перестаёт значить «отправка службой с
трек-номером». Теперь это **доставка исполнителем**:

1. В окне оформления — галочка «Нужна доставка». Она доступна, только если
   покупатель верифицирован и проверен. Иначе под ней подсказка: «Доставка
   доступна проверенным пользователям» и путь к статусу — заполнить паспорт с
   фото, дальше заявка уходит сама (§2).
2. Адрес по умолчанию — адрес из регистрации, с возможностью ввести другой
   (подсказки DaData).
3. Точка А — **адрес отправки товара**: у вещи своё поле «Откуда забирать»
   (`shop_products.dispatch_address` с координатами и ФИАС). При создании товара
   форма подставляет адрес пункта выдачи, отмеченного в админке как пункт по
   умолчанию (`shop_pickup_points.is_default`, такой пункт один); админ может
   его поменять. Вещь, у которой включена доставка, без адреса отправки не
   сохраняется.
4. В той же транзакции, что и покупка, создаётся заказ услуги «Доставка»:
   заказчик — покупатель, А — адрес отправки товара, Б — его адрес, комментарий —
   «Покупка №N: футболка M». `shop_orders.delivery_order_id` связывает их.
5. **Деньги.** Доставка включена в цену товара, поэтому удержание по заказу
   финансирует не покупатель, а счёт `SHOP`:

   | Тип | Счёт | Знак | Смысл |
   | :--- | :--- | :--- | :--- |
   | `SHOP_DELIVERY_HOLD` | `SHOP` → `ESCROW` | `0` | платформа оплачивает доставку покупки |
   | `SHOP_DELIVERY_REFUND` | `ESCROW` → `SHOP` | `0` | доставка отменена, деньги вернулись в выручку |

   `orders.funded_by = 'SHOP'` говорит ядру, куда вернуть удержание при
   отмене: в `SHOP`, а не на баланс покупателя. Подтверждение идёт обычным
   путём: исполнитель получает цену доставки за вычетом комиссии.
6. **Статусы связаны:** заказ доставки создан — покупка `PROCESSING`;
   исполнитель забрал вещь — `SHIPPED`; покупатель подтвердил заказ доставки —
   покупка `COMPLETED`, купон гасится автоматически.
7. **Отмена.** Возврат покупки через поддержку отменяет и заказ доставки, если
   исполнитель ещё не забрал вещь. Если забрал — сначала спор или возврат
   вещи, как у обычного заказа.
8. Спор по заказу доставки идёт общим механизмом споров.

Трек-номер и ручной перевод в `SHIPPED` для доставки убираются: их заменяет
заказ исполнителю. Самовывоз не меняется.

## 6. Что меняется в оферте

* п. 6.3: доставка выполняется исполнителем платформы, стоимость включена в
  цену товара, доставка доступна проверенным пользователям;
* новый пункт о паспортных данных: зачем они нужны (доставка, статус
  «проверенный»), как хранятся, кто их видит.

Редакция оферты повышается на единицу. Покупки, сделанные раньше, остаются на
своей редакции.

## 7. Открытые вопросы

Предложены решения по умолчанию. План исходит из них, пока не решено иначе.

0. ✅ **Проверка правила привилегии прогоном по сетке** при сохранении — принято (§1.3).
1. **Цена услуги «Доставка»** — фиксированная из каталога. Цена по расстоянию
   между А и Б — следующая версия.
2. ✅ **Откуда забирать** — адрес у товара; по умолчанию — адрес пункта выдачи,
   отмеченного в админке как пункт по умолчанию (§5.3).
3. ✅ **Обязательные поля паспорта** — серия, номер, дата выдачи (§3.1).
4. **Иностранные документы** — не поддерживаются в первой версии.
5. **Срок хранения паспорта** после удаления аккаунта — удаляется сразу
   каскадом. Если юрист скажет хранить N лет — добавим отложенное удаление.

## 8. Вне этой версии

* Цена доставки по расстоянию и срочная доставка.
* Автоматическая проверка паспорта (распознавание, проверка по базам).
* Скрипты для других видов привилегий, не про комиссию: приоритет в выдаче
  заказов, радиус. Рантайм к ним готов, нужна своя точка применения.
