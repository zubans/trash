## Этап 1. Схема и статусы

### B1.1 Миграция `052_soft_banned_and_disputed_statuses.sql`

- `ALTER TYPE status_type ADD VALUE IF NOT EXISTS 'SOFT_BANNED'`.
- `ALTER TYPE order_status_type ADD VALUE IF NOT EXISTS 'DISPUTED' AFTER 'EXECUTED'`.
- `ALTER TYPE transaction_type ADD VALUE IF NOT EXISTS 'DISPUTE_REWARD'` (добавлено в B1.2).
- Маркер `-- +migrate no-transaction`.

**Готово:** миграция применяется на чистой базе и на копии рабочей схемы;
повторный прогон не падает.

### B1.2 Миграция `053_disputes_and_penalties.sql`

- Таблицы `order_disputes` (уникальный частичный индекс: один `OPEN` на заказ),
  `penalty_points`, `user_penalty_status`, `user_penalty_flags`.

- Проверка новых настроек при сохранении (целые числа в границах).
- Системный счёт `DISPUTES`.
- Настройки `penalty_points_threshold`, `photo_requirement_months`,
  `penalty_points_ttl_months`, `silent_block_months`,
  `photo_proof_max_time_diff_min`, `photo_proof_max_distance_m`.
- Права `disputes.view/edit`, `penalties.edit` для `MODERATOR`; разделы в
  каталоге `service/permission.go`.
- Строка ачивки `first_repentance` с `is_active = true`.

**Готово:** миграция применяется; сверка книг на пустом счёте `DISPUTES`
проходит; новые разделы видны в матрице прав.

## Этап 3. Спор

### B3.1 Открытие спора и подтверждение из `DISPUTED`

- `POST /customer/orders/{id}/dispute` — только свой заказ в `EXECUTED`,
  претензия обязательна; заказ → `DISPUTED`, спор `OPEN`, событие
  `dispute.opened` в той же транзакции.
- `confirmTx` принимает `DISPUTED` и закрывает открытый спор
  (`CUSTOMER_CONFIRMED`) в той же транзакции.
- `cancelTx` принимает `DISPUTED` для признания и решения арбитра.
- Представление заказа (`order_view.go`) отдаёт действия `dispute`, `concede`
  и признак спора для бейджа.

**Готово:** тесты: чужой заказ, неверный статус, повторное открытие,
подтверждение из очереди закрывает спор.

Сделано. Отступления от плана: спор разрешён только для обычных услуг —
скриптовые закрываются сами; `confirmTx`/`cancelTx` отказывают заказу с
открытым спором, закрывать спор обязан вызывающий; `orderRepo.Cancel` принимает
`EXECUTED` и `DISPUTED` (какие статусы допустимы, решает `cancelTx`).

### B3.2 Признание исполнителем

- `POST /executor/orders/{id}/dispute/concede` — только свой заказ в `DISPUTED`.
- Заказ отменяется с полным возвратом, спор `EXECUTOR_CONCEDED`, балла нет,
  событие `dispute.conceded`.

**Готово:** тесты: возврат денег, отсутствие балла, событие опубликовано.

### B3.3 Проводка решения «неизвестно»

- Метод `Ledger` для решения «неизвестно»: возврат удержания из `ESCROW`
  заказчику; сумма заказа с `DISPUTES`, комиссия по ставке и уровню исполнителя
  на `COMMISSION`, остаток исполнителю.
- Ставка и уровень записываются в заказ.
- Сверка (`reconcile`) учитывает `DISPUTES`.

**Готово:** тест на суммы по всем счетам; сверка сходится после проводки.

### B3.4 Решение арбитра

- `GET /admin/disputes?status=OPEN|CLOSED`.
- `POST /admin/disputes/{id}/resolve`: `executor` → `confirmTx` + балл
  заказчику; `customer` → `cancelTx` + балл исполнителю; `unknown` → B3.3 +
  баллы обоим. Закрытый спор — `409`.
- Блокировка строки заказа; гонка с подтверждением заказчиком.

**Готово:** тесты всех трёх решений и гонки «заказчик подтвердил, пока арбитр
решал» — ровно одно закрытие, деньги один раз.

### B3.5 Уведомления по спору

- Открытие: исполнителю — внутренняя почта и e-mail (если подтверждён).
- Закрытие любым способом: обеим сторонам — почта и e-mail; системное
  сообщение в чат заказа.
- Отправка после коммита.
- Шаблоны писем ru.

**Готово:** тесты: откаченная транзакция ничего не отправляет; письма уходят
нужным адресатам.

### B3.6 Ачивка «Первое покаяние»

- `backend/achievements/first_repentance`: 5 баллов, разовая, аудитория
  `EXECUTOR`, событие `dispute.conceded`.

**Готово:** тест движка ачивок: выдаётся один раз, баллы в `user_points`.

## Этап 4. Штрафы

### B4.1 Журнал баллов и пересчёт состояния

- `repository/penalty.go`, `service/penalty.go`.
- Начисление балла (роль, заказ, спор, кто назначил) и пересчёт
  `user_penalty_status` в одной транзакции с решением спора.
- Отмена балла админом (`revoked_at`) с пересчётом.

**Готово:** тесты начисления, отмены, пересчёта; двойное начисление по одному
спору одной роли невозможно.

### B4.2 Период фото и тихая блокировка

- Баллов ≥ N — `photo_required_until = now + photo_requirement_months`; новый
  балл в периоде продлевает от момента начисления.
- Баллов ≥ 2×N — тихая блокировка роли на `silent_block_months`.

**Готово:** тесты порогов N и 2×N, продления периода.

### B4.3 Рецидив → `SOFT_BANNED`

- Новый балл в любой роли у пользователя с `had_silent_block` → `users.status =
  SOFT_BANNED`, `soft_banned_at`, `soft_ban_reason`; сессии не завершаются.

**Готово:** тесты: рецидив банит; без флага — обычное начисление.

### B4.4 Воркер штрафов

- Раз в час, под лидерством (`worker/leader.go`).
- Сжигает баллы роли, если последнему больше `penalty_points_ttl_months`;
  снимает период фото вместе с ними.
- Снимает тихую блокировку по `silent_block_ends_at`: сжигает оставшиеся баллы,
  ставит `had_silent_block`.

**Готово:** тесты с подменой времени: сгорание, снятие блокировки через 6
месяцев при живых баллах.

### B4.5 Тихая блокировка в выдаче

- Исполнитель: `FindNearbyOrdersForExecutor`, аукцион, карта — пусто;
  автоподбор пропускает; `Accept`, `CreateBid` — нейтральный отказ (тот же, что
  для недоступного заказа).
- Заказчик: каталог услуг пуст; создание заказа — нейтральный отказ.
- Уже взятые заказы не затронуты.

**Готово:** тесты на каждую точку; ответ не отличим от «заказов нет».

### B4.6 Эндпоинты штрафов

- `GET /me/penalty-status`: период фото по ролям и `SOFT_BANNED`; тихая
  блокировка не раскрывается.
- `GET /admin/users/{id}/penalties`, `POST .../{point_id}/revoke`,
  `POST .../reset-silent-flag`.

**Готово:** тесты прав и того, что `/me/penalty-status` не выдаёт тихую
блокировку.

## Этап 5. Фото-подтверждение (бэкенд)

### B5.1 Модуль `backend/photoproof/`, CRUD символов

- Пакет с repository, service, handler; подключение в `main.go`.
- CRUD `/admin/watermark-symbols` с правами `watermarks.*`, мягкое удаление,
  картинка-подсказка. Картинка задаётся ссылкой (`hint_image_url`); отдельная
  загрузка файла — при работе над экраном F8.2, если понадобится.

**Готово:** тесты CRUD; удалённый символ не выбирается для новых заказов, но
остаётся у старых.

### B5.2 Требование фото и жест

- `OrderService.WithPhotoProof(...)`.
- `Accept`: если период фото у исполнителя или заказчика — `photo_required`,
  случайный активный символ, служебные данные защиты.
- Заказы исполнителя отдают жест и данные, нужные клиенту офлайн.
- `ExecuteOrder`: без снимка `AREA` — `422`; сохраняет `executed_at_device`.

**Готово:** тесты: требование только для заказов, взятых после включения
периода; `422` без снимка.

### B5.3 Приём снимков и EXIF

- `POST /executor/orders/{id}/photo-proof` (multipart): вид, камера, время и
  координаты устройства, ключ снимка для идемпотентности.
- Только JPEG, лимит размера, файл без перекодирования, sha256.
- Разбор EXIF (`github.com/rwcarlsen/goexif`): время съёмки, координаты.

**Готово:** тесты: повтор с тем же ключом не создаёт дубль; EXIF разбирается на
тестовых файлах; снимок без EXIF принимается с пустыми полями.

### B5.6 Трек исполнителя

- Миграция `055_executor_positions.sql`: таблица трека и настройки
  `photo_proof_max_track_gap_min`, `executor_track_days`.
- Приём точек пачкой: `POST /executor/positions` — массив точек с временем
  устройства; обычный отчёт `POST /executor/shifts/location` пишет туда же
  строку `LIVE`, не меняя своего нынешнего поведения.
- Отчёты обязательны в периоде фото-подтверждения независимо от
  `geofence_tracking_enabled`; статус периода уже отдаёт `/me/penalty-status`.
- Ближайшая по времени точка трека к моменту съёмки — запрос для сверки.
- Очистка трека по сроку — в проходе воркера штрафов.

**Готово:** тесты: точка со снимком и пачка из офлайна попадают в трек,
ближайшая точка выбирается по времени устройства, старые строки чистятся,
отчёты принимаются в периоде при выключенной общей настройке.

### B5.4 Проверка скрытой защиты снимка

- Проверка при загрузке, результат в `order_photo_proofs`.
- Реализация по закрытому описанию; общие тестовые векторы с клиентом (F6.3).

**Готово:** тесты на векторах: целый снимок, пересохранённый, чужой.

### B5.5 Данные сверки для арбитража

- `GET /admin/disputes` отдаёт снимки, жест, времена, координаты, расстояние до
  адреса, результат проверки защиты и флаги превышения порогов.
- Плюс трек: ближайшая к съёмке точка (возраст, расстояние до места съёмки и до
  адреса заказа), отметка «трека рядом нет» и аномалии скорости вокруг времени
  съёмки.

**Готово:** тесты флагов на граничных значениях порогов.
