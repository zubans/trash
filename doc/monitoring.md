# Метрики и мониторинг (Metrics & Monitoring)

Документ описывает, что система рассказывает о себе, кто это собирает и что именно поднимает тревогу.

---

## 1. Что здесь есть

| Слой | Чем собирается | Где смотреть |
| :--- | :--- | :--- |
| Приложение (Go) | Встроенные метрики бэкенда на отдельном порту `:9091` | Дашборд **Healthlogin · Бэкенд** |
| Хост | `node-exporter` | Дашборд **Healthlogin · Инфраструктура** |
| Контейнеры | `cAdvisor` | там же |
| PostgreSQL | `postgres-exporter` | там же |
| Nginx | `nginx-prometheus-exporter` через `stub_status` | там же |
| Внешняя доступность, TLS, SMTP | `blackbox-exporter` | там же |
| Хранение и правила | Prometheus, 30 дней | `http://127.0.0.1:9090` |
| Оповещения | Alertmanager → Telegram | `http://127.0.0.1:9093` |

Стек живёт в **отдельном** compose-файле [`docker-compose.monitoring.yml`](../docker-compose.monitoring.yml). Это сознательно: приложение можно поднимать, перезапускать и отлаживать без мониторинга, а сломанная Grafana не должна мешать бэкенду стартовать.

---

## 2. Запуск

### На сервере через CI

Обычный путь — ничего не запускать руками. Job `deploy-monitoring` в [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml) идёт **параллельно** с деплоем приложения и срабатывает только на изменения в `monitoring/**` и `docker-compose.monitoring.yml`. Правка алерта или дашборда не пересобирает образы приложения и не перезапускает сервисы.

Достаточно один раз завести секреты репозитория `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` и `GRAFANA_ADMIN_PASSWORD` — подробности и полный список в [`deployment.md`](./deployment.md#4-автоматизация-cicd-github-actions).

### Вручную

Секреты мониторинга живут в **отдельном** файле `.env.monitoring` рядом с `.env` (на сервере его пишет CI):

```
TELEGRAM_BOT_TOKEN=123456789:AA...
TELEGRAM_CHAT_ID=-1001234567890
GRAFANA_ADMIN_PASSWORD=<сгенерируйте>
```

Файл отдельный не для порядка: деплой приложения перезаписывает `.env` целиком на каждом запуске, и переменные мониторинга, дописанные туда, терялись бы при следующей гонке двух параллельных job'ов. Compose получает оба файла, значения из второго побеждают.

Пароль базы берётся из общего `.env` — см. [`.env.deploy.example`](../.env.deploy.example).

Дальше:

```bash
make monitoring-up
```

Останов только мониторинга, приложение продолжает работать:

```bash
make monitoring-down
```

### Доступ к интерфейсам

Grafana, Prometheus и Alertmanager слушают **только `127.0.0.1`** и наружу не опубликованы. Вместе они раскрывают внутреннее устройство системы, пароль базы в переменных экспортера и форму входа Grafana — в интернете им делать нечего. Ходите туннелем:

```bash
ssh -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 -L 9093:127.0.0.1:9093 user@moya-usluga.ru
```

После этого Grafana открывается на `http://localhost:3000` (логин `admin`, пароль из `GRAFANA_ADMIN_PASSWORD`).

> Если Grafana всё же понадобится снаружи — выносите её через nginx с авторизацией, а не меняйте привязку порта в compose-файле.

## 3. Метрики приложения

Бэкенд отдаёт метрики на **отдельном слушателе** `METRICS_ADDR` (по умолчанию `:9091`), не на основном роутере. Порт доступен только внутри compose-сети, nginx его не проксирует. Так скрейп не попадает под CORS, ограничитель частоты и прочую прикладную middleware, а `/metrics` не оказывается в интернете.

Все имена начинаются с `healthlogin_`.

### HTTP

| Метрика | Смысл |
| :--- | :--- |
| `http_requests_total{method,route,status}` | Запросы по маршрутам. `route` — **шаблон** chi (`/api/orders/{id}`), а не сырой путь: иначе каждый заказ порождал бы свой временной ряд. Всё, что не совпало ни с одним маршрутом, схлопывается в `not_found`, чтобы сканер по случайным путям не раздувал метрику. |
| `http_request_duration_seconds` | Гистограмма времени ответа. |
| `http_requests_in_flight` | Запросов в обработке прямо сейчас. |

### Бизнес

`order_events_total{event}` (`created`, `created_auction`, `assigned`, `accepted`, `executed`, `confirmed`, `cancelled`, `rejected`, `downgraded`), `bid_events_total`, `shift_events_total` (включая `geofence_violation` и `geofence_penalty`), `matching_assignments_total{result}`.

Плюс два датчика глубины рынка, которые обновляет мэтчер на каждом проходе: `orders_searching` и `shifts_active`. Их сочетание ловит отказ, невидимый в счётчиках запросов: всё отвечает `200`, а работа не делается, потому что делать её некому.

### Деньги

> `reconcile_ok` стартует как **NaN**, а не как 0. У gauge значение по умолчанию — ноль, а ноль на этой метрике означает конкретное и громкое утверждение: «книги не сходятся». До того, как проход реально завершился, такого свидетельства нет — упавший проход не доказывает ничего. Без этого сверка, свалившаяся на первой же попытке, поднимала page о пропавших деньгах, которых никто не терял. Алерт дополнительно требует `reconcile_last_run_timestamp_seconds > 0`, а случай «проход не может отработать» поднимает отдельное правило `ReconciliationFailing` — тикетом.

`ledger_entries_total{type,account}` и `ledger_amount_rubles_total{type,account}` считаются в одной точке — `Ledger.record`, через которую проходит **каждое** движение денег. Записать одностороннюю проводку мимо счётчика нельзя.

Результат ночной сверки: `reconcile_ok`, `reconcile_findings{kind}`, `reconcile_drift_rubles{kind}`, `reconcile_last_run_timestamp_seconds`. Если проход **упал**, датчики сохраняют прежние значения и растёт `reconcile_failures_total` — обнулять их означало бы утверждать, что книги в порядке, тогда как их просто никто не проверил.

### Зависимости и фон

`upstream_requests_total{upstream,operation,result}` для DaData и Nominatim (отдельные значения `cache_hit`, `busy`, `rate_limited`, `unauthorized` — они лечатся по-разному), `mail_sends_total{kind,result}`, `worker_runs_total`, `worker_last_success_timestamp_seconds`, `chat_websocket_connections`.

## 4. Ops-бот в Telegram

[`backend/cmd/opsbot`](../backend/cmd/opsbot) даёт три действия, ради которых иначе пришлось бы открывать SSH — как раз тогда, когда это неудобнее всего.

| Команда | Что делает |
| :--- | :--- |
| `/reconcile` | Принудительная сверка балансов **с публикацией метрик** |
| `/metrics` | Ключевые метрики бэкенда одним сообщением |
| `/restart` → `/restart_confirm` | `make restart` на сервере |
| `/help` | Справка |

Сверку бот не считает сам, а просит бэкенд: датчики сверки живут в его процессе, и проход, который их не обновил, оставил бы экран и тревогу спорящими об одних и тех же деньгах. Тот же эндпоинт дёргает кнопка в админке, поэтому любой ручной запуск сразу снимает `LedgerDrift`, не дожидаясь ночного прохода.

### Почему он устроен именно так

Бот **перезапускает прод**, поэтому собран как привилегированный инструмент:

- **Слушает ноль портов.** Long polling к Telegram — только исходящие соединения, входящей поверхности атаки нет вовсе. Webhook потребовал бы публичный URL и маршрут в nginx для сервиса, который выполняет команды.
- **Allowlist до разбора сообщения.** Чужой чат не получает даже отказа: ответ подтвердил бы, что бот существует, и подсказал бы, какие команды пробовать. Без единого разрешённого чата бот **не стартует**.
- **Перезапуск — фиксированный список аргументов без shell.** Из сообщения не берётся ничего: команда решает только, запускать ли, но никогда — что именно.
- **Двухшаговое подтверждение.** Случайное касание не должно ронять прод; запрос живёт `OPSBOT_CONFIRM_WINDOW` и привязан к чату, где его сделали.
- **Сообщения старше процесса отбрасываются.** Иначе `/restart`, отправленный пока бот лежал, сработал бы при старте — для команды перезапуска это петля.

> ⚠️ **Боту примонтирован Docker-сокет — это root на хосте.** Именно поэтому он отдельный сервис, а не горутина в бэкенде: бэкенд смотрит в интернет, а это — не должно. Кто может писать боту, тот может перезапустить прод, поэтому `OPSBOT_ALLOWED_USERS` в групповом чате стоит заполнить.

Секрет `OPS_KEY` общий у бэкенда и бота, закрывает `/internal/*` на метрик-порту. Не задан у бэкенда — маршруты просто не регистрируются: настроенный «наполовину» общий секрет не должен превращаться в открытую дверь.

## 5. Тревоги

Правила лежат в [`monitoring/prometheus/rules/`](../monitoring/prometheus/rules/) — 31 правило в двух файлах. Две градации:

- **page** — пользователи страдают прямо сейчас или речь о деньгах. Повторяется каждые 4 часа, пока горит.
- **ticket** — починить на этой неделе. Тот же чат, без настойчивости, повтор раз в сутки.

У каждого правила есть `for`, достаточный, чтобы пережить деплой и перезапуск контейнера.

Что попадает в **page**: бэкенд не отвечает, публичный адрес недоступен, больше 5% ответов `5xx`, не принимается почта на 587, **расхождение в сверке балансов**, ошибки записи в финансовый журнал, DaData отвечает ошибками (без подсказок нельзя завершить регистрацию), диск заполнен больше чем на 90%, PostgreSQL недоступен, контейнер в цикле перезапусков.

Настроены `inhibit_rules`: упавший бэкенд гасит всё, что от него зависит, а мёртвый endpoint гасит тревогу «отвечает, но не проксирует» по тому же серверу. Без этого один сетевой сбой прилетает двадцатью сообщениями, а пачка из двадцати сообщений глушится так же надёжно, как их отсутствие.

### Правка правил

```bash
make monitoring-check   # синтаксис + юнит-тесты правил
make monitoring-reload  # применить без потери базы рядов
```

`monitoring-check` делает две вещи. Первая — `promtool check config`: Prometheus не откажется стартовать из-за неверного выражения в правиле, он просто никогда его не вычислит, а это худший из возможных отказов для мониторинга. Вторая — `promtool test rules` по файлам в [`monitoring/prometheus/rules/tests/`](../monitoring/prometheus/rules/tests/). CI прогоняет то же самое перед применением.

Тесты появились не для красоты. Правило, которое срабатывает там, где не должно, — это не косметика: так канал оповещений превращается в то, что перестают читать. Оба отрицательных кейса в тестах — реальные ложные срабатывания:

- **`reconcile` и порог в 15 минут.** Сверка балансов идёт раз в сутки, а порог «обработчик не отрабатывал 15 минут» был общим на всех. Алерт загорался минут через двадцать после каждого рестарта и больше не гас. Теперь `reconcile` исключён из общего правила — у него есть своё, `ReconciliationNotRunning`, с горизонтом в 48 часов.
- **Доля 5xx без порога по объёму.** Ночью здесь единицы запросов в минуту, и две ошибки из двадцати одной — это уже 9.5%. Добавлен нижний порог трафика; чтобы ошибки при этом не стали невидимыми, тихие 5xx поднимает отдельное правило `ServerErrorsAtLowTraffic` — тикетом, а не page.

**Добавляя правило, добавляйте к нему отрицательный кейс** — тот, при котором оно гореть не должно.

| Переменная | Где | Описание | По умолчанию |
| :--- | :--- | :--- | :--- |
| `METRICS_ADDR` | backend | Адрес слушателя `/metrics`. Пустое значение выключает его. | `:9091` |

| `TELEGRAM_CHAT_ID` | alertmanager | Куда слать. Для группы — отрицательное число. **Обязателен.** | — |
| `GRAFANA_ADMIN_PASSWORD` | grafana | Пароль администратора. **Обязателен.** | — |

## 7. Заметки по эксплуатации

**Дашборды провижинятся из файлов и правки в UI не сохраняются** (`allowUiUpdates: false`). Источник истины — JSON в [`monitoring/grafana/dashboards/`](../monitoring/grafana/dashboards/), чтобы панель, которую кто-то подвинул в три часа ночи, не стала определением.

**Про «orphan containers».** Команды с одним только `docker-compose.yml` — `make start`, `make restart`, регистрация релиза — печатают:

```
WARN Found orphan containers ([healthlogin_prometheus ...]) for this project.
```

Это не поломка. Мониторинг — второй overlay в том же Compose-проекте, и команда, которой передали только базовый файл, не знает о его сервисах, поэтому считает их «осиротевшими». Предупреждение подавлено через `COMPOSE_IGNORE_ORPHANS=true` в Makefile: оно срабатывало на каждый запуск, а предупреждение, которое горит всегда, никто не читает.

> ⚠️ **Никогда не выполняйте то, что советует само предупреждение.** `docker compose --remove-orphans` с базовым файлом **удалит весь стек мониторинга** — данные Prometheus, дашборды Grafana, заглушенные алерты. Проверено: обычный `down` с базовым файлом контейнеры мониторинга не трогает, приложение можно спокойно останавливать и перезапускать; разрушителен только `--remove-orphans`.

Там же рядом бывает `Network trash_default Resource is still in use` — по той же причине: сеть держат контейнеры мониторинга. Compose переиспользует её при следующем `up`, это тоже безвредно и как раз то, что нужно: обе половины стека обязаны быть в одной сети, иначе Prometheus не достучится до `backend:9091`.

**Ретенция — 15 дней или 2 ГБ**, что наступит раньше. Изначально стояло 30 дней и 8 ГБ, и это было ошибкой: сервер один, диск общий, и уже через сутки прилетел алерт о нехватке места. Мониторинг, забивший диск, утаскивает за собой базу — это хуже короткой истории. Поднимать только после `df -h`.

**Порядок middleware важен.** `metrics.Middleware` стоит **внутри** `Recoverer`: иначе паника не считалась бы за отданную клиенту `500`, а просто исчезала бы из счётчиков.

**`make monitoring-up` не поднимает зависимости (`--no-deps`).** Иначе `depends_on` подтянул бы `db` и `frontend` ровно в тот момент, когда параллельный деплой приложения их останавливает. Экспортеры ретраятся, пока цель не вернётся, — это и есть правильное поведение.

**Изменение конфига не пересоздаёт контейнер.** Prometheus перечитывает правила только по `make monitoring-reload`, а Alertmanager рендерит свой конфиг из шаблона при старте, поэтому его надо перезапустить. CI делает и то, и другое; при ручной правке не забудьте сами.
