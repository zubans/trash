# Резервный канал связи мобильного приложения (VLESS Fallback Channel)

Документ описывает механизм, который позволяет Android-приложению продолжать работать, когда прямой путь до бэкенда недоступен: приложение поднимает локальный SOCKS-прокси на базе **libXray** и туннелирует через VLESS только трафик до своего API.

> **Статус:** реализовано, изменения ещё не закоммичены (ветка `feature/address-dadata`, рабочее дерево).

---

## 1. Принцип работы

Приложение по умолчанию работает **напрямую** (`DIRECT`). Раз в 10 минут (и один раз при старте) `ChannelManager`:

1. обновляет список endpoint'ов — так подхватываются смены адресов серверов;
2. проверяет здоровье бэкенда **напрямую**; если проверка проходит — режим `DIRECT`, туннель гасится;
3. иначе переключается на туннель: если текущий сервер ещё отвечает — остаётся на нём, иначе перебирает серверы из списка, отводя на каждый **5 секунд**.

Всё это невидимо для WebView и UI — пользователь переключения не замечает.

**Туннелируется только хост API** (`NetConfig.apiHost` и его поддомены); любой другой трафик идёт напрямую даже в режиме `PROXY`.

## 2. Серверная часть

### Эндпоинт

```
GET /api/app/endpoints
X-App-Key: <APP_ENDPOINTS_KEY>
```

Обработчик: [`backend/handler/app_endpoints.go`](../backend/handler/app_endpoints.go)

Список содержит адреса серверов и Reality-ключи, поэтому он не должен ни лежать на сервере в открытом виде для всех, ни отдаваться любому, кто знает URL:

- доступ закрыт общим ключом в заголовке `X-App-Key`, сравнение — **constant-time** (`subtle.ConstantTimeCompare`);
- тело шифруется **AES-256-GCM** перед отправкой; формат — `base64( nonce(12) || ciphertext+tag )`, nonce случайный на каждый ответ, поэтому один и тот же файл каждый раз даёт разный блоб;
- `Cache-Control: no-store`;
- plaintext-файл смонтирован read-only и **никогда не отдаётся напрямую**.

Если ключ доступа отсутствует или ключ шифрования не 32 байта, обработчик создаётся выключенным и на все запросы отвечает `503` — неверная конфигурация падает громко, а не течёт открытым текстом.

| Ответ | Когда |
| :--- | :--- |
| `200` | Зашифрованный base64-блоб. |
| `403` | Не совпал `X-App-Key`. |
| `503` | Секреты не настроены или файл списка не читается. |
| `500` | Ошибка шифрования. |

### Файл списка

`vless-endpoints.json` в корне репозитория, монтируется в контейнер бэкенда:

```yaml
volumes:
  - ./vless-endpoints.json:/app/vless-endpoints.json:ro
```

Формат — `{ "version": 1, "configs": [ <полный конфиг Xray>, ... ] }`. Каждый элемент `configs` — самостоятельный конфиг Xray с `remarks`, `log` и `outbounds` (`proxy` / `block` / `direct`). Поддерживаются в том числе `xhttp + tls` и `tcp + reality`.

Правка файла применяется **на следующем опросе приложения — пересборка не нужна.**

> Раньше файл раздавался nginx'ом как статика по `/app/vless.json`. Этот том из сервиса `frontend` удалён: список теперь отдаёт только бэкенд, зашифрованным и за ключом.

## 3. Клиентская часть (Android)

Пакет [`frontend/android/app/src/main/java/com/healthlogin/app/net/`](../frontend/android/app/src/main/java/com/healthlogin/app/net/):

| Файл | Роль |
| :--- | :--- |
| `VlessChannel.java` | Синглтон с состоянием канала (`DIRECT` / `PROXY`), адресом локального SOCKS и хостом API. Отдаёт `ProxySelector`. |
| `ChannelManager.java` | Политика переключения: периодический опрос, health-check, перебор серверов. |
| `RemoteConfigRepo.java` | Загрузка и кэш списка: шлёт `X-App-Key`, расшифровывает AES-256-GCM, хранит **расшифрованный** JSON в app-private `SharedPreferences` (`vless_prefs`). |
| `XrayController.java` | Владеет единственным экземпляром libXray: нормализует конфиг (переписывает inbound на фиксированный локальный SOCKS), пишет файл, стартует/останавливает ядро. |
| `LibXrayBridge.java` | Обёртка над AAR через reflection. |
| `AesGcm.java` | Расшифровка полезной нагрузки; формат совпадает с `encrypt()` в Go-обработчике. |
| `NetConfig.java` | Статические сетевые координаты сборки. |
| `Secrets.java` | `APP_KEY` и `ENC_KEY_HEX`, зашитые в сборку. |

### Куда подключён канал

- [`MainActivity.java`](../frontend/android/app/src/main/java/com/healthlogin/app/MainActivity.java) ставит **процессный** `ProxySelector.setDefault(...)` **до** того, как WebView и Capacitor сделают первый запрос. Благодаря этому HTTP-плагин Capacitor (на `HttpURLConnection`, через него ходит axios) прозрачно соблюдает канал. В режиме `DIRECT` селектор возвращает `NO_PROXY`.
- [`NativeWebSocketPlugin.java`](../frontend/android/app/src/main/java/com/healthlogin/app/plugins/NativeWebSocketPlugin.java) передаёт тот же `proxySelector()` в свой OkHttp-клиент, чтобы сокет чата шёл тем же путём, что и API.

### `NetConfig.production()`

| Поле | Значение |
| :--- | :--- |
| `apiHost` | `moya-usluga.ru` — только этот хост туннелируется |
| `healthUrl` | `https://moya-usluga.ru/health` |
| `configUrl` | `https://moya-usluga.ru/api/app/endpoints` |
| `socksPort` | `1080` |

Значения зеркалят `VITE_API_URL` нативной сборки — при смене хоста бэкенда их надо править вместе.

### libXray AAR

Готовый релизный AAR из [XTLS/libXray](https://github.com/XTLS/libXray) кладётся в `frontend/android/app/libs/` и подхватывается по маске:

```gradle
implementation fileTree(include: ['*.aar'], dir: 'libs')
```

Точное имя файла значения не имеет. **Если AAR отсутствует — приложение собирается и работает**, просто никогда не выходит из `DIRECT` (`LibXrayBridge` пишет в лог `libXray AAR not found`). Reflection выбран сознательно: имена и сигнатуры экспортируемых символов libXray меняются между релизами.

`geoip.dat` / `geosite.dat` нужны только если в конфиги добавляются гео-правила маршрутизации; текущие endpoint'ы их не используют.

### Seed-ассет

`frontend/android/app/src/main/assets/vless-endpoints.enc` — начальный список, зашифрованный тем же ключом, поэтому **открытый текст в APK не попадает**. Используется, пока не получен свежий список с сервера.

## 4. Конфигурация и секреты

| Переменная (сервер) | Константа (Android) | Описание |
| :--- | :--- | :--- |
| `APP_ENDPOINTS_KEY` | `Secrets.APP_KEY` | Ключ доступа, приходит в заголовке `X-App-Key`. |
| `APP_ENDPOINTS_ENC_KEY` | `Secrets.ENC_KEY_HEX` | Ключ AES-256-GCM, 32 байта = 64 hex-символа. |
| `APP_ENDPOINTS_FILE` | — | Путь к plaintext-файлу внутри контейнера, по умолчанию `/app/vless-endpoints.json`. |

Генерация:

```bash
openssl rand -base64 24 | tr -d '/+=' | head -c 32   # APP_ENDPOINTS_KEY
```

```bash
openssl rand -hex 32                                  # APP_ENDPOINTS_ENC_KEY
```

Обе пары значений **обязаны совпадать** между сервером и сборкой приложения и ротируются одновременно в обоих местах.

> **Ограничение модели угроз.** Клиентские секреты извлекаются из APK — это не жёсткая граница безопасности. Механизм поднимает планку против массового скрейпинга и убирает открытый список с сервера, не более. Значения, лежащие сейчас в `Secrets.java` и `.env.deploy.example`, считаются скомпрометированными: перед реальным релизом сгенерируйте новую пару.

## 5. Что нужно сделать при выкатке

1. Сгенерировать свежую пару ключей и прописать её в `.env` на сервере и в `Secrets.java`.
2. Положить `vless-endpoints.json` рядом с `docker-compose.yml` (он монтируется read-only). Взять за основу [`vless-endpoints.example.json`](../vless-endpoints.example.json) и подставить реальные значения. **Боевой файл `vless-endpoints.json` в git не коммитится** (он в [`.gitignore`](../.gitignore)); в репозитории лежит только шаблон, и он обязан содержать исключительно плейсхолдеры (`REPLACE-…`) — ни реальных адресов серверов, ни xhttp-`path`, ни SNI. Адреса и `path` — это тоже чувствительные данные: `path` фактически работает пропуском к xhttp-endpoint'у. **Файл должен существовать до первого запуска контейнеров:** Docker на месте отсутствующего источника bind-mount создаёт каталог, после чего `/api/app/endpoints` навсегда отвечает `503`, и каждый пересоздаваемый контейнер делает этот каталог заново. `make start` теперь это проверяет и не даёт стартовать поверх каталога.
3. Пересоздать зашифрованный seed-ассет `vless-endpoints.enc` тем же ключом.
4. Положить `LibXray.aar` в `frontend/android/app/libs/` перед сборкой APK.

## 6. Мониторинг канала

Канал, которым на исправной системе никто не пользуется, ломается незаметно: сервер переехал, истёк сертификат, провайдер закрыл порт — и первым об этом узнаёт пользователь, у которого уже что-то не работает.

Поэтому цепочка проверяется отдельной пробой [`backend/cmd/vlessprobe`](../backend/cmd/vlessprobe): она скачивает список через публичный API с тем же `X-App-Key` и той же расшифровкой, что и приложение, подключается к каждому endpoint'у и — главное — прогоняет каждый конфиг через xray и тянет `/health` **через туннель**. Открытый порт ничего не доказывает: прокси за ним может не передавать ни байта.

Подробности, метрики и тревоги — в [`monitoring.md`](./monitoring.md).
