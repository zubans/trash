# Загрузка данных на клиенте: кэш и прелоадеры

Документ описывает, как экраны приложения показывают данные: что видит
пользователь, пока данных нет, и почему повторное открытие экрана не начинается
с пустоты.

---

## 1. Задача

Дашборды заказчика и исполнителя каждый раз собирались с нуля: при открытии
экрана списки были пустыми, а разметка успевала показать «Нет заказов» и
подставной адрес профиля до того, как приходил первый ответ. На мобильной сети
это занимает секунды, и переключение между вкладками выглядело как потеря
данных.

Решение состоит из двух частей, которые работают вместе:

1. **Кэш** — последнее полученное значение сохраняется и поднимается при
   следующем открытии экрана **синхронно**, до первого запроса.
2. **Прелоадеры** — когда показывать действительно нечего (кэша нет), на месте
   списка стоит скелетон формы этого списка, а не пустое состояние.
3. **Приоритеты загрузки** — сетевые запросы уходят ступенями: сначала то, ради
   чего экран открыли, история заказов — самой последней.
4. **Предзагрузка изображений** — фотографии из чатов активных заказов
   прогреваются заранее и хранятся, пока заказ не закроется.

---

## 2. Кэш (`src/services/cache.ts`)

Хранилище — `localStorage`, ключи с префиксом `cache:v1:`.

| Свойство | Правило | Почему так |
| :--- | :--- | :--- |
| Владелец | Ключ включает `userID`; без вошедшего пользователя кэш не читается и не пишется. | На общем устройстве следующий вошедший не должен увидеть чужие заказы даже мельком. |
| Срок годности | 12 часов, запись старше стирается при чтении. | Кэш нужен ради первого кадра, а не ради работы офлайн: вчерашний список заказов хуже прелоадера. |
| Конец сессии | `clearSession()` в `services/api.ts` стирает весь кэш. | Данные заказов и профиля не переживают выход из аккаунта и истечение сессии. |
| Сбои | Любая ошибка чтения/записи (приватный режим, переполнение) молча игнорируется; при переполнении кэш чистится и запись повторяется один раз. | Кэш — ускорение; его отсутствие не должно ломать экран, который уже получил данные. |

Публичное API: `readCache`, `writeCache`, `dropCache`, `clearCachedData`.

## 3. Ресурс экрана (`src/composables/useCachedResource.ts`)

Каждый список экрана объявляется как ресурс — ключ кэша плюс функция загрузки:

```ts
const ordersResource = useCachedResource<any[]>({
  key: 'customer:orders',
  initial: [],
  fetcher: async () => (await api.get('/customer/orders')).data || [],
  onData: () => fetchReviewsForHistory(),
})
```

Три способа сходить за данными различаются поводом:

| Метод | Кто зовёт | Поведение |
| :--- | :--- | :--- |
| `load()` | Открытие простого экрана. | Синхронно поднимает кэш, затем уходит в сеть. |
| `hydrate()` | Экран с приоритетами загрузки. | Только кэш, синхронно. Показать известное надо сразу и всем; в очередь выстраиваются лишь походы в сеть. |
| `refresh()` | Опрос по таймеру, возврат из фона. | Только сеть; запрос, уже находящийся в пути, переиспользуется. |
| `reload()` | После действия пользователя (взял заказ, открыл смену, создал заказ). | Только сеть, но **не** присоединяется к запросу, отправленному до действия: тот ответ о действии не знает и вернул бы состояние до нажатия. Дожидается его и спрашивает заново. |

Три состояния намеренно не сведены в один флаг:

| Флаг | Значение | Что рисует экран |
| :--- | :--- | :--- |
| `loading` | Показывать нечего: ни кэша, ни ответа сети. | Скелетон (`SkeletonList`). |
| `refreshing` | Данные на экране есть, поверх них идёт догрузка. | Мелкий значок `RefreshingBadge` в заголовке секции; список не перерисовывается. |
| `fromCache` | То, что на экране, ещё не подтверждено сетью. | Ничего особенного; признак для логики экрана. |

Дополнительно:

- **Один запрос за раз.** Опрос по таймеру и возврат из фона легко приходятся на
  один момент; без этого экран получил бы несколько ответов подряд, в том числе
  в порядке, обратном отправке. Исключение — `reload()`, см. таблицу выше.
- **Сорванное обновление не очищает экран.** Ошибка попадает в `error`, а
  показанное значение остаётся: список, верный мгновение назад, лучше пустого.
  Прелоадер при этом гасится, иначе экран без кэша крутил бы его вечно.
- **`acceptCached`** отбраковывает кэш, потерявший смысл. Так сделано с активной
  сменой: запись со статусом `ACTIVE` и прошедшим `planned_end_at` не
  поднимается — сервер такую смену уже закрыл, и показать её активной значило бы
  соврать о состоянии, от которого зависит приём заказов.

## 4. Приоритеты загрузки (`src/utils/loadPriority.ts`)

Открытый экран запрашивает сразу несколько вещей, и все они делят одно
соединение: на мобильной сети десяток параллельных запросов означает, что и
главный из них приедет последним. `loadByPriority` принимает ступени в порядке
убывания важности — ступень выполняется целиком параллельно, следующая ждёт
предыдущую.

**Показ и сеть разведены.** Кэш поднимается синхронно у всех ресурсов сразу
(`hydrate()`), и только сетевые запросы выстраиваются в очередь. Иначе экран,
открытый повторно, держал бы историю на скелетоне, хотя её данные уже лежат в
хранилище.

Ошибка одной задачи не отменяет остальные и не обрывает очередь (`allSettled`):
провалившийся второстепенный запрос не должен уносить с собой то, что идёт
следом.

### Дашборд исполнителя

| Ступень | Что грузится | Почему здесь |
| :--- | :--- | :--- |
| 1 | Смена, назначенные заказы, каталог услуг. | То, ради чего экран открывают. Каталог здесь же: без него заказ, отданный без вложенной услуги, назывался бы просто «Заказ». |
| 2 | Профиль, настройки геотрекинга. | Приносят сохранённую рабочую позицию и решают, включать ли отчёты о местоположении. |
| 3 | Заказы поблизости, старт отчётов о местоположении, текущая позиция. | Список считается от позиции из профиля — раньше ступени 2 запрашивать его нечем. |
| 4 | Непрочитанные сообщения, уведомление поддержки. | Фон экрана. |
| 5 | **Финансовая история.** | Справка о прошлом; секция свёрнута по умолчанию, а за ней тянется по запросу отзыва на каждый завершённый заказ. |
| 6 | Прогрев фотографий активных заказов. | Подготовка к будущему нажатию, а не содержимое экрана, и самая тяжёлая по трафику часть — ей и уступать очередь. |

### Дашборд заказчика

| Ступень | Что грузится | Почему здесь |
| :--- | :--- | :--- |
| 1 | Заказы, профиль, справочник категорий. | Заказы и история приходят одним ответом `/customer/orders`, поэтому разделять их нечем и незачем. |
| 2 | **Оценки к завершённым заказам.** | Это и есть «история последней»: по запросу на заказ ради значка с рейтингом. На первой загрузке их откладывает очередь, дальше они обновляются вместе со списком, а уже полученные не перезапрашиваются. |
| 3 | Прогрев фотографий активных заказов. | Подготовка к будущему нажатию, а не содержимое экрана, и самая тяжёлая по трафику часть — ей и уступать очередь. |

## 5. Изображения заказа (`src/services/orderImages.ts`)

Чат заказа чаще всего открывают ради фотографий, а загружаться они начинали
ровно в момент открытия: пользователь видел пустые прямоугольники именно тогда,
когда на них смотрел. Теперь фотографии активных заказов прогреваются заранее —
последней ступенью очереди, когда экран уже собран.

### Как это работает

1. **Где берутся пути.** Вложения живут в сообщениях чата. Список путей по
   каждому открытому заказу сохраняется в тот же кэш (`orders:images`), поэтому
   после перезапуска приложения картинки начинают грузиться сразу, не дожидаясь,
   пока по каждому заказу приедут сообщения.
2. **Сообщения читаются один раз на заказ за сеанс.** Дальше открытый чат
   докладывает новые вложения сам (`rememberOrderImages`) — и когда сообщения
   прочитаны, и когда фотография пришла по сокету.
3. **Заказы обходятся по очереди**, а не разом: их немного (лимит активных
   заказов), зато предзагрузка не отбирает соединение у того, что на экране.
4. **Загрузка через `fetch` в блоб.** Тем же путём работает запасной вариант
   `@error` у `<img>`, который был здесь и раньше: добытое им тоже попадает в
   кэш заказа.

### Срок жизни

Кэш держится ровно столько, сколько открыт заказ. Это не срок «на всякий
случай», а граница смысла: пока заказ в работе, к его фотографиям возвращаются;
подтверждённый или отменённый уходит в историю, и держать их незачем.

Освобождение висит на обновлении списка заказов — единственном месте, где видно,
что заказ закрылся. Заказ, пропавший из списка, тоже считается закрытым. Object
URL при этом **отзывается явно**: без `revokeObjectURL` блоб живёт до
перезагрузки страницы, а в мобильном WebView она может не случиться никогда.
Конец сессии освобождает всё — `clearOrderImages` подключён к очистке кэша через
`onCacheCleared`, чтобы `api.ts`, `cache.ts` и хранилище картинок не замкнулись
в кольцо импортов.

### Заглушка

Пока фотография не появилась на экране, её место занимает мерцающий
прямоугольник (`.img-pending`): без него сообщение подпрыгивает в момент, когда
картинка приезжает. Заглушка гаснет по факту показа (`@load`), а не по факту
загрузки блоба, — снимок, взятый напрямую из сети в обход предзагрузки, тоже
должен её убрать. Если картинку не удалось забрать и запасным путём, заглушка
гасится тоже: вечно мерцающий прямоугольник хуже честно не загрузившейся
картинки.

## 6. Что кэшируется

| Экран | Ключ | Содержимое |
| :--- | :--- | :--- |
| Исполнитель | `executor:shift:active` | Текущая смена (с проверкой `planned_end_at`). |
| Исполнитель | `executor:orders:assigned` | Назначенные заказы. |
| Исполнитель | `executor:orders:available` | Заказы поблизости. |
| Исполнитель | `executor:history:orders` | Финансовая история — уже отсортированная, чтобы первый кадр из кэша совпадал с сетевым. |
| Заказчик | `customer:orders` | Все заказы (активные и история — один список, разделяемый вычислимыми свойствами). |
| Заказчик | `customer:profile` | Профиль с сохранёнными адресами. |
| Оба | `orders:images` | Пути к фотографиям по открытым заказам (см. раздел 5). Сами картинки лежат блобами в памяти. |

Порядок сетевой загрузки этих ресурсов задаёт очередь приоритетов из раздела 4;
кэш при этом поднимается у всех сразу.

## 7. Прелоадеры

- **`components/SkeletonList.vue`** — заглушка списка: иконка, две-три полосы
  текста, при необходимости кнопка справа. Форма повторяет строку заказа,
  поэтому появление настоящих данных не сдвигает вёрстку. Управляется свойствами
  `rows`, `lines`, `icon`, `action`. При `prefers-reduced-motion` анимация
  выключается.
- **`components/RefreshingBadge.vue`** — маленький значок тихой догрузки в
  заголовке секции. Он не занимает места в потоке и не заставляет ждать.
- **Панель смены** на дашборде исполнителя, пока состояние смены неизвестно,
  показывает спиннер вместо кнопок: кнопка «Открыть» рядом с уже открытой сменой
  сбивает с толку сильнее, чем короткое ожидание.
- **`.img-pending`** — мерцающий прямоугольник на месте фотографии, которая ещё
  не появилась (см. раздел 5).
- **`styles/loading.css`** — общий `.spinner-sm` (и модификатор `.dark` для
  светлого фона). Разметка использовала этот класс в восьми экранах, а правила
  для него лежали в двух компонентах со scoped-стилями: везде остальном спиннер
  на кнопке был пустым `<span>`, и кнопка «замирала» без признака отправки.
- **Каталог услуг** в окне создания заказа сохраняет прежний индикатор
  «Загрузка каталога…»: он открывается по действию пользователя, кэшировать там
  нечего.

## 8. Тесты

`src/composables/useCachedResource.spec.ts` покрывает и хранилище, и ресурс:
привязку к пользователю, срок годности, очистку, порядок «кэш → сеть»,
сохранение показанных данных при сетевой ошибке, отсутствие параллельных
запросов, отличие `reload()` от `refresh()` и работу `acceptCached`.

`src/utils/loadPriority.spec.ts` проверяет очередь: параллельность внутри
ступени, ожидание предыдущей ступени, продолжение очереди после ошибки задачи.

`src/services/orderImages.spec.ts` проверяет главное правило кэша изображений:
закрытие заказа освобождает его картинки (и отзывает object URL), заказ,
пропавший из списка, считается закрытым, один путь загружается один раз,
сохранённый список путей греет картинки после перезапуска без запроса чата, а
недоступный чат одного заказа не отменяет остальные.
